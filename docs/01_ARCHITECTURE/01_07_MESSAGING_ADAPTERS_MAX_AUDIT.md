# 01.07. Технический аудит библиотек и шлюзов MAX Messenger и архитектура IMessagingAdapter

---

## 1. Введение и цели аудита

Цель аудита — выбор оптимального технологического решения для интеграции мессенджера **MAX** в B2B SaaS CRM платформу **GETVOXLY** (`/inbox`, CRM-сделки, AI-агенты) взамен или в дополнение к существующему сервису `max-bridge` (FastAPI + `maxapi-python`).

Ключевые критерии оценки:
1. **Строгая мультитенантность (Multi-Tenancy):** изоляция сессий, ключей и диалогов клиентов с поддержкой PostgreSQL 16 Row-Level Security (RLS).
2. **Безопасность сессий и токенов:** защита от утечек и перехвата, шифрование креденшелов на уровне БД через **AES-256-GCM**.
3. **Устойчивость к детекции и блокировкам (Anti-Ban):** минимизация риска бана номеров клиентов при работе в режиме CRM и AI-ботов.
4. **Совместимость со стеком Fastify 5 (TypeScript ESM):** отсутствие блокирующего I/O, нативная поддержка асинхронного event-driven пайплайна.
5. **Нулевой простой (Zero-Downtime Migration):** сохранение 100% работоспособности существующих подключенных аккаунтов.

## 2. Детальный аудит 5 вариантов библиотек и шлюзов

### Вариант A: `unosmm/max-messenger-mobile-api-unofficial`
* **Стек:** Python (неофициальный reverse-engineering мобильного клиента Android `ru.oneme.app`).
* **Анализ репозитория:** Заброшенный проект (всего 2 коммита, последнее обновление >1.5 лет назад).
* **Архитектурные риски:**
  * Эмуляция мобильного APK без прохождения проверок Google Play Integrity / SafetyNet. Мобильный API MAX детектирует аномалии заголовков, fingerprinting устройства и отсутствие TLS JA3/JA4 слепков официального клиента, что приводит к мгновенной блокировке номеров.
  * Отсутствует поддержка мультитенантности: рассчитан на один статический запуск через локальный `.env`.
  * Требует отдельного Python runtime (дополнительный сайдкар).
* **Вердикт:** **КАТЕГОРИЧЕСКИ НЕ РЕКОМЕНДУЕТСЯ** для коммерческого SaaS.

---

### Вариант B: `Sharkow1743/MaxAPI`
* **Стек:** Python (asyncio wrapper над API веб-версии MAX).
* **Анализ репозитория:** Репозиторий **официально заархивирован автором** с пометкой: *"Больше не поддерживается и не работает. Протокол изменился. Лучший рабочий вариант сейчас — PyMax"*.
* **Архитектурные риски:** Неработоспособен в проде (устаревшие эндпоинты авторизации и схема рукопожатия WebSocket).
* **Вердикт:** **НЕПРИГОДЕН** (мертвый код).

---

### Вариант C: `pr0bel1230/max-api-docs`
* **Стек:** Спецификация и документация бинарного / JSON WebSocket-протокола веб-клиента MAX (`wss://ws-api.oneme.ru/websocket`, версия 11).
* **Анализ протокола:**
  * Позволяет построить **полноценный нативный TypeScript-клиент** прямо внутри Fastify/Node.js процесса без Python-контейнеров.
  * Использует стандартные опкоды:
    * `6` — `INIT` (регистрация deviceId и clientVer);
    * `19` — `LOGIN` (авторизация по веб-токену `__oneme_auth`);
    * `49` — `GET_HISTORY` (получение истории чата с постраничной пагинацией);
    * `53` — `GET_CHATS` (список активных диалогов);
    * `64` — `MSG_SEND` (отправка сообщений и медиа-вложений);
    * `128` — `INCOMING_EVENT` (асинхронное получение входящих событий в реальном времени).
* **Преимущества:**
  * **Zero Dependency / Zero Sidecar:** устраняет накладные расходы на поддержание отдельного Docker-контейнера FastAPI/SQLite.
  * **Производительность:** прямой WebSocket нативный стек в Node.js 22, минимальный footprint по RAM (~10-15 МБ на 100 сокетов против ~150 МБ у Python-процесса).
  * **Полный контроль над протоколом:** возможность гибкой эмуляции User-Agent и Keep-Alive.
* **Риски:** Необходимость самостоятельного отслеживания изменений веб-протокола MAX.
* **Вердикт:** **РЕКОМЕНДОВАН** как целевой основной in-house движок (`MaxTsAdapter`).

---

### Вариант D: `artgas1/max-mcp-server`
* **Стек:** Model Context Protocol (MCP) сервер на Python/Node, оборачивающий PyMax для Cursor/Claude Desktop.
* **Анализ репозитория:** Утилита для персонального использования локальными desktop LLM-агентами (stdio / SSE транспорт).
* **Архитектурные риски:**
  * Не является шлюзом мессенджера: не умеет обслуживать пул аккаунтов разных тенантов.
  * Отсутствует поддержка входящих вебхуков, RLS-изоляции и фоновых очередей BullMQ.
* **Вердикт:** **НЕПРИГОДЕН** для архитектуры B2B CRM.

---

### Вариант E: `GREEN-API для MAX`
* **Стек:** Внешний коммерческий SaaS-шлюз с REST API и Webhook-уведомлениями.
* **Анализ сервиса:**
  * Готовый промышленный API: методы `SendMessage`, `ReceiveNotification`, `GetChatHistory`.
  * Сессии поддерживаются на стороне облака GREEN-API; автоматический мониторинг здоровья инстансов и проксирование запросов.
* **Преимущества:**
  * **99.9% SLA:** провайдер берет на себя анти-бан, ротацию прокси и адаптацию к обновлениям протокола MAX.
  * **Простейшая интеграция в Fastify:** стандартные HTTP POST и приём входящих вебхуков.
* **Недостатки:** Ежемесячная абонентская плата за каждый подключенный инстанс (вендор-лок и прямые операционные расходы).
* **Вердикт:** **РЕКОМЕНДОВАН** как Enterprise-опция (`MaxGreenApiAdapter`) для клиентов с высокими требованиями к SLA.

## 4. Архитектурная оценка безопасности и изоляции

### 4.1. Предотвращение перехвата сессий (Session Hijacking)
* В протоколе MAX критическим артефактом авторизации является сессионный токен веб-клиента (`__oneme_auth` / bearer token) либо QR-сессия.
* Утечка этого токена позволяет злоумышленнику читать все сообщения арендатора в обход CRM.
* **Решение в GETVOXLY:**
  1. Токены **никогда** не передаются на фронтенд.
  2. Все токены и ключи доступа шифруются на уровне бэкенда через **AES-256-GCM** (функции `encryptSecret` / `decryptSecret` из `backend/src/services/credentials-cipher.ts`).
  3. В базе данных `channel_accounts.credentials` хранятся только зашифрованные пейлоады:
     ```json
     {
       "provider": "native-ts",
       "encrypted_token": "v1:a3f9...:iv...:tag..."
     }
     ```

### 4.2. Изоляция данных по арендаторам (PostgreSQL RLS)
* Каждая запись `channel_accounts`, `deals`, `deal_messages` и `contacts` строго защищена `tenant_id UUID NOT NULL` и политиками PostgreSQL Row-Level Security.
* Сессии `MaxTsAdapter` и диспетчеризация `MessagingRegistry` привязаны к паре `(tenantId, channelAccountId)`. Ни один обработчик не имеет права рассылать или читать события без валидации `tenant_id`.

## 5. Реализованная архитектура: IMessagingAdapter & Registry

В кодовой базе внедрен слой абстракции, объединяющий все адаптеры в единый контракт:

```
                          ┌──────────────────────────┐
                          │   GETVOXLY Core CRM      │
                          │ (/inbox, Deals, AI Bots) │
                          └─────────────┬────────────┘
                                        │
                                        ▼
                          ┌──────────────────────────┐
                          │    MessagingRegistry     │
                          └─────────────┬────────────┘
                                        │
         ┌──────────────────────────────┼──────────────────────────────┐
         ▼                              ▼                              ▼
┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
│  MaxBridgeAdapter│          │   MaxTsAdapter   │          │MaxGreenApiAdapter│
│ (PyMax Sidecar)  │          │(Native WebSocket)│          │ (Managed Cloud)  │
│ [Zero-Downtime]  │          │ [Zero-Sidecar]   │          │  [Enterprise]    │
└──────────────────┘          └──────────────────┘          └──────────────────┘
```

1. **`IMessagingAdapter` (`backend/src/modules/messaging/adapters/IMessagingAdapter.ts`):**
   * Универсальный TypeScript интерфейс (`sendMessage`, `getHistory`, `resolveContact`, `subscribeToEvents`, `healthCheck`).
2. **`MaxBridgeAdapter` (`backend/src/modules/messaging/adapters/max/MaxBridgeAdapter.ts`):**
   * Обеспечивает **100% обратную совместимость** со всеми уже подключенными аккаунтами на проде (текущие сессии в контейнере `voxly-max-bridge`).
3. **`MaxTsAdapter` (`backend/src/modules/messaging/adapters/max/MaxTsAdapter.ts`):**
   * Нативный асинхронный клиент протокола MAX на WebSockets с поддержкой опкодов `6, 19, 49, 53, 64, 128` и автоматическим Heartbeat.
4. **`MaxGreenApiAdapter` (`backend/src/modules/messaging/adapters/max/MaxGreenApiAdapter.ts`):**
   * REST/Webhook адаптер для облачного шлюза GREEN-API.
5. **`MessagingRegistry` (`backend/src/modules/messaging/messaging-registry.ts`):**
   * Интегрирован с `server.ts` через `registerOutboundSender("max", ...)`.
   * Маршрутизирует входящие сообщения прямо в `CrmPipelineService.processIncoming(...)`.

## 6. Стратегия миграции (Zero-Downtime Migration Plan)

1. **Фаза 1 (Текущее состояние — Выполнено):**
   * Внедрен `MessagingRegistry`. Все исходящие и входящие потоки MAX идут через `IMessagingAdapter`. Существующие аккаунты прозрачно работают через `MaxBridgeAdapter`.
2. **Фаза 2 (Пилотное включение MaxTsAdapter):**
   * Для новых подключений или тестовых тенантов выставляется флаг `credentials.provider = "native-ts"`. Проверяется стабильность сокетов и отсутствие банов.
3. **Фаза 3 (Окончательный вывод PyMax sidecar):**
   * После миграции всех сессий контейнер `getvoxly-max-bridge-1` останавливается, высвобождая ресурсы VPS.
