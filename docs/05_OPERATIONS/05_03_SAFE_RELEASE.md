# Безопасный релиз и откат

Изменения 2026-09-21 проверены локально mock-тестами. Реальный deploy/restore в рамках этой работы не запускался.

## Допуск

`GETVOXLY_RELEASE_APPROVED=yes` задаётся оператором только после явного согласования. `GETVOXLY_RESTORE_VERIFIED` содержит ссылку/идентификатор успешного восстановления резервной копии на отдельном стенде. Скрипт проверяет наличие этих подтверждений, но не может доказать их достоверность: evidence обязателен в release log.

До запуска: staging smoke, frontend/backend tests, проверка миграций на копии, совместимость прежнего образа с новой схемой, проверка достаточного диска. Не запускать две выкладки одновременно; автоматическая координация параллельных release пока не реализована.

## Артефакты

До rsync скрипт создаёт `/opt/getvoxly-releases/<UTC timestamp>-<pid>`:
- source.tgz без node_modules/.next/.audit/.env;
- database.dump и database.list;
- images.txt и Docker rollback tags для выбранных сервисов.

`pg_restore --list` подтверждает читаемость TOC, не пригодность восстановления всех данных. Secrets не добавляются в source archive; их отдельная резервная копия и доступ — ответственность оператора.

## Откат

1. Остановить rollout. Зафиксировать failed release, текущие image IDs, migrations и время последнего успешного события.
2. При совместимой expand-only схеме вернуть прежние образы выбранных сервисов по сохранённым IDs/tags, используя временный compose override. Проверить compose config до выполнения и не затрагивать DB/соседние сервисы.
3. Повторить HTTP/container и функциональный smoke. Исходники хоста восстанавливать из source.tgz только после проверки отличий и сохранения текущего дерева; не затирать .env.
4. Не выполнять автоматический `migrate:down` или восстановление старой DB после новых платежей/сообщений. Нужны пауза записи, backup текущего состояния, reconciliation и согласованный recovery plan. Иначе откат потеряет новые операции.
5. Не удалять release artifacts, пока не завершено наблюдение и не подтверждён внешний backup. Политику retention задавать отдельно, без бесконтрольного накопления на VPS.

## Ограничения

- `--no-deps --force-recreate` не обеспечивает zero downtime для единственного экземпляра; ожидаемое окно необходимо согласовать.
- Отдельное `frontend` обновление не перезапускает backend и его transport.
- HTTP 200 и healthy необходимы, но недостаточны: проверять сценарии платежа/доступа/переписки на разрешённом тестовом tenant.
- Real provider tests используют sandbox; не отправлять клиентам тестовые сообщения.
