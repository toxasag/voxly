# MAILING-LIMITS — справочник лимитов, пауз и ротации

Единый источник для антифлуда (Фаза 1A–1D). Значения — безопасные дефолты; клиент может менять суточные лимиты в портале (но не поднимать выше «потолка» без подтверждения).

## Паузы между отправками (рандомизированные)

| Действие | Диапазон | Примечание |
|---|---|---|
| Сообщение в личный чат (gift / gramjs / wa / max) | 30–60 сек | random в диапазоне, не фиксированная |
| Сторис | 180–300 сек | random |
| Broadcast-рассылка (массовая) | 30–60 сек × на получателя | плюс учёт лимита аккаунта |

## Суточные лимиты на аккаунт (дефолт «как положено»)

> Область применения: **массовые рассылки** (broadcast/stage-rule). User-triggered
> funnel-сообщения (ответ на /start, отложенные нуджи) в суточный лимит не входят —
> они инициированы пользователем и уже имеют собственное расписание.

| Канал | Сообщений/день (default) | Сторис/день (default) |
|---|---|---|
| Telegram gift-бот (Bot API) | 100 | — |
| Telegram GramJS (личный, без Premium) | 200 | 1 |
| Telegram GramJS (личный, Premium) | 200 | 100 |
| WhatsApp (Evolution) | 300 | 20 |
| MAX (PyMax) | 200 | ? (исследуется 1D.5) |

Клиент может **снизить** лимиты в портале; **повысить** — с подтверждением «на ваш риск» и не выше потолка (×3 от дефолта).

## Telegram Premium

- Статус определяется автоматически: GramJS `client.getMe().premium` при коннекте + фоновое обновление.
- Без Premium: 1 сторис/сутки. С Premium: до 100 (настраивается).
- Статус виден в списке аккаунтов (бейдж «Premium» / «без Premium»).

## FloodWait / Rate Limits

| Платформа | Признак | Обработка |
|---|---|---|
| Telegram Bot API | HTTP 429 + `retry_after` | пауза `retry_after` + jitter 0.5–2с, ретрай того же получателя; `retry_after ≥ 60с` → failover сразу |
| Telegram Bot API | `error_code` 400/403, текст `spam`/`flood` | аккаунт в `floodedUntil` (cooldown = `retry_after`, иначе 6ч), failover на другой аккаунт |
| GramJS | `FloodWaitError` (поле `seconds`) | пауза `seconds` + jitter, ретрай; >300с → failover |
| Evolution (WA) | 429 / rate_limited | backoff 1с→5с→30с (макс 3 попытки), затем failed со статусом |
| MAX (PyMax) | rate limit исключения | backoff, исследовать в 1A.2 |

## Ротация аккаунтов

- Пул рассылки: `broadcast.botIds[]`.
- Выбор: **least-loaded** (минимальный счётчик `tg:day:{bot}:{date}:sent` в Redis).
- Failover: FloodWait/SpamBlock/auth-ошибка → `floodedUntil` → следующий аккаунт пула, очередь не останавливается.
- Весь пул в блоке → **пауза джоба** (`job.moveToDelayed`) до ближайшего `floodedUntil` + jitter 0–30с, потом продолжить (реализовано 1B.4: planner/recepient/story).
- Весь пул на суточном лимите (флуда нет) → фейл рассылки с `daily_limit_reached` (лимит сбросится только завтра).

## Прогрев (warm-up)

- `warmupSince` на аккаунте; множитель суточного лимита:
  - день 1: 10%
  - день 2–3: 30%
  - день 4–7: 60%
  - день 8+: 100%
- Реализовано (1C.2): лимит пула рассылки = `floor(дефолт канала × warmupFactor(возраст))`, минимум 1. Ручной лимит (override в портале) отключает прогрев и применяется как есть.
- История прогрева — `WarmupLog` (Job 1C.4).

## Сторисы: публикация

- Сторисы **публичные**: публикуем на своём аккаунте, видят все. Без ограничения аудитории (`statusJidList`/privacyRules НЕ используем).
- Поддерживаются: Telegram (GramJS), WhatsApp (Evolution `sendStatus`). MAX — исследуется (1D.5). Telegram Business-бот (Bot API) — не поддерживает сторис физически.
- Клики по ссылке в сторис считаем через `TrackingLink` (свой шортнер).
