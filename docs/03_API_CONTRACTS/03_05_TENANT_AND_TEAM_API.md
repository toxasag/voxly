# 03_05 — TENANT, TEAM & PROFILE API

Разделы аккаунта арендатора: сотрудники, роли, места в тарифе и подписка.
Смонтированы в `app.ts` под `/api/v1/tenant`; публичные эндпоинты приглашения —
в группе `/auth`.

> Источник: `backend/src/modules/tenant/tenant.routes.ts`,

## 1. Роли и права

Роли и права — независимые механизмы: `users.role` управляет `requireRole`,
массив `users.permissions` — `requirePermission`. Карта ниже задаёт значение по
умолчанию при создании пользователя, а не выводит права из роли на каждом
запросе.

| Роль | Отображается | Права по умолчанию |
|---|---|---|
| `owner` | Владелец | все 19, включая `tenant:admin` и `billing:manage` |
| `admin` | Администратор | 18 — всё, кроме `billing:manage` |
| `manager` | Менеджер | CRM целиком + чтение сервисного центра, финансов, AI |
| `technician` | Мастер | ремонты и задачи; без удаления и финансов |
| `viewer` | Наблюдатель | только чтение |

`ASSIGNABLE_ROLES` исключает `owner`: владелец создаётся только при регистрации
арендатора, и второй владелец через приглашение означал бы неограниченную
передачу прав на биллинг. Ограничение продублировано в Zod-схеме, в типе
`AssignableRole` на клиенте и проверкой в сервисе.

Единый справочник — `backend/src/config/permissions.ts`. До него
`VALID_PERMISSIONS` был объявлен дважды (в `plugins/authenticate.ts` и в
`modules/auth/auth.service.ts`), а карты «роль → права» не существовало вовсе.

## 2. Состояния сотрудника

Статус **выводится**, а не хранится отдельной колонкой: два источника истины
разошлись бы при первом же входе.

| Состояние | Условие | Занимает место в тарифе |
|---|---|---|
| Приглашён | `activated_at IS NULL` | да |
| Активен | `activated_at IS NOT NULL` | да |
| Удалён | `deleted_at IS NOT NULL` | нет |

Приглашённый занимает место намеренно: иначе лимит обходился бы рассылкой
приглашений, а счёт вырос бы неожиданно в момент, когда сотрудники начали их
принимать.

Ключевые следствия миграции `0008_team_management.sql`:

- `users.password_hash` и `users.phone` стали nullable — их задаёт сам сотрудник
  при активации. Инвариант `users_active_needs_password`
  (`activated_at IS NULL OR password_hash IS NOT NULL`) закреплён в схеме, а не
  в коде, иначе баг оставил бы учётную запись, в которую нельзя войти, но
  которая занимает место в тарифе.
- Мягкое удаление обязательно: на `users(id)` ссылаются `deals.created_by`,
  `crm_tasks.assignee_id`, `invoices.created_by`, `repair_notes.author_id`,
  `repair_photos.uploaded_by` и `deal_stage_history.changed_by` **без**
  `ON DELETE`, поэтому Postgres отклонил бы удаление сотрудника, успевшего
  создать хоть одну запись.
- `UNIQUE (tenant_id, email)` и `UNIQUE (tenant_id, phone)` заменены частичными
  индексами по живым строкам: иначе уволенного нельзя было бы пригласить снова
  под тем же адресом.
- Все выборки входа (`findByEmail`, `findByPhone`, `findById`) и `resolveUser` в
  `authenticate.ts` фильтруют `deleted_at IS NULL AND activated_at IS NOT NULL`.
  Без первого условия уволенный сотрудник работал бы до истечения 15-минутного
  access-токена, без второго — приглашённый с `password_hash = NULL` вызывал бы
  ошибку argon2 вместо честного отказа.

## 3. `GET /api/v1/tenant/info`

План, статус и остаток пробного периода. Доступен любому члену арендатора: это
его собственная подписка.

`tenants.trial_ends_at` добавлен миграцией `0008` — прежде пробный период
существовал только у каждого модуля (`installed_modules.trial_ends_at`), и
показать «осталось X дней» по аккаунту было нечем. Единственным источником был
платформенный `GET /api/v1/admin/tenants` под `requirePlatformOwner`, куда
арендатор получает `403`.

```json
{
  "data": {
    "id": "…", "name": "QA Проверка", "slug": "qacheck",
    "plan": "trial", "status": "trial",
    "trialEndsAt": "2026-09-01T15:05:44.662Z",
    "trialDaysLeft": 11,
    "trialActive": true,
    "createdAt": "2026-08-21T15:05:44.662Z"
  }
}
```

`trialDaysLeft` считается на сервере: браузерные часы можно перевести, и клиент
показал бы работающий триал после его окончания.

## 4. `GET /api/v1/tenant/team`

Состав команды и занятые места. **`tenant:admin`**.

```json
{
  "data": {
    "members": [{
      "id": "…", "fullName": "QA Владелец", "email": "qa@qacheck.test",
      "phone": "79995551234", "role": "owner", "status": "active",
      "isOwner": true, "isSelf": true,
      "invitedAt": null, "activatedAt": "…", "createdAt": "…"
    }],
    "seats": {
      "used": 2, "included": 10, "extra": 0,
      "extraSeatPrice": 200, "nextSeatPrice": 0
    },
    "assignableRoles": ["admin", "manager", "technician", "viewer"]
  }
}
```

`isOwner` и `isSelf` вычисляются на сервере: интерфейс скрывает по ним действия,
но те же правила проверяются в обработчиках, поэтому запрос в обход UI не
пройдёт.

Тариф мест читается из каталога маркетплейса (`marketplace_modules` для
`core_crm`: `included_units = 10`, `unit_price = 200`), а не из константы —
захардкоженные значения разошлись бы с биллингом при первом изменении тарифа.
Резервные `10`/`200` применяются только если строки каталога нет.

## 5. `POST /api/v1/tenant/team/invite`

Создаёт неактивную учётную запись и отправляет ссылку. **`tenant:admin`**.

```json
{ "name": "Пётр Мастеров", "email": "master@company.ru", "role": "technician",
  "confirm_extra_seat": false }
```

**Ответ `201`:** `{ data: { member, seats, emailSent } }`.
`emailSent: false` означает, что SMTP не настроен — ссылку придётся передать
вручную; учётная запись при этом создана.

**`409 SEAT_LIMIT_CONFIRMATION_REQUIRED`,** когда включённые места исчерпаны и
`confirm_extra_seat` не передан:

```json
{ "error": { "code": "SEAT_LIMIT_CONFIRMATION_REQUIRED",
  "message": "Базовый лимит (10 пользователей) исчерпан. Стоимость увеличится на +200 ₽/мес за нового пользователя." } }
```

Проверка на сервере обязательна: предупредить в модальном окне недостаточно,
запрос можно отправить и минуя интерфейс, и тогда счёт вырос бы без ведома
владельца.

Повторное приглашение того же адреса **обновляет** существующую строку под
`FOR UPDATE`, а не создаёт вторую: частичный уникальный индекс
`idx_users_tenant_email_active` иначе отклонил бы вставку ошибкой `23505`.
Активный сотрудник с этим адресом даёт `409 USER_ALREADY_EXISTS`.

Токен приглашения — 32 случайных байта, в БД только SHA-256
(`users.invite_token_hash`), TTL 72 часа. Ссылка:
`{PUBLIC_APP_URL}/accept-invite?token=<token>`.

## 6. `PATCH /api/v1/tenant/team/:id`

Смена роли. **`tenant:admin`**. Тело: `{ "role": "manager" }`.

Права приводятся к новой роли (`ROLE_PERMISSIONS`), иначе они остались бы от
прежней и понижение роли не забрало бы доступ.

- `409 CANNOT_MODIFY_SELF` — нельзя изменить собственную роль: администратор
  понизил бы себя и потерял доступ к разделу, оставив арендатора без управления
  сотрудниками.
- `409 CANNOT_MODIFY_OWNER` — роль владельца неизменна.

---

## 7. `DELETE /api/v1/tenant/team/:id`

Мягкое удаление. **`tenant:admin`**. Ответ: `{ data: { seats } }`.

В одной транзакции: `deleted_at = now()`, токен приглашения гасится, **все
refresh-токены сотрудника отзываются**. Вместе с фильтром `deleted_at IS NULL` в
`resolveUser` это отбирает доступ немедленно, а не через 15 минут.

Те же ограничения: `CANNOT_MODIFY_SELF`, `CANNOT_MODIFY_OWNER`.

## 8. `POST /api/v1/tenant/team/:id/resend`

Новый токен и повторное письмо. **`tenant:admin`**.
`404`, если приглашение не найдено или уже принято.

## 9. Публичные эндпоинты приглашения

Публичные по необходимости: учётная запись существует, но не активна, поэтому
предъявить учётные данные приглашённый не может. Входят в `PUBLIC_PATHS`.

### `GET /auth/invite?token=…` (лимит 20/мин)

```json
{ "data": { "email": "master@company.ru", "fullName": "Пётр Мастеров",
  "companyName": "QA Проверка", "role": "technician", "roleLabel": "Мастер" } }
```

Наружу отдаются только имя компании, роль и e-mail: человек должен понимать,
куда его пригласили, до ввода пароля. Идентификаторы и хеши остаются внутри.

### `POST /auth/invite/accept` (лимит 10/мин)

```json
{ "token": "…", "password": "…8+ символов…", "phone": "+7 999 777 66 55" }
```

Телефон обязателен — по нему приходит код второго фактора, без него сотрудник не
смог бы войти. Выборка под `FOR UPDATE`: иначе два параллельных перехода по одной
ссылке оба увидели бы непогашенный токен. Занятый в пределах арендатора номер
даёт `409 PHONE_TAKEN` с ошибкой поля, а не `500`.

Ссылка одноразовая: `invite_token_hash` обнуляется вместе с установкой
`activated_at`. Повторный переход — `400 INVALID_INVITE_TOKEN`.

# ЧАСТЬ II. ЛИЧНЫЙ ПРОФИЛЬ — `/api/v1/profile`

Отдельная группа, а не расширение `/auth`: та сознательно не регистрирует
`authenticatePlugin` (все её пути публичные), тогда как каждое действие здесь
выполняется от имени вошедшего пользователя. Прав не требуется — это собственные
данные, а не чужие: `tenant:admin` закрыл бы профиль от рядового сотрудника.

Источник: `backend/src/modules/profile/profile.service.ts`,
`backend/src/modules/profile/profile.routes.ts`, миграция
`0009_user_profile.sql`.

## 12. `GET /api/v1/profile`

```json
{
  "data": {
    "id": "…", "name": "Антон Проверкин", "email": "qa@qaprof.test",
    "phone": "79995558899", "role": "owner",
    "avatarUrl": "data:image/webp;base64,…",
    "createdAt": "…",
    "hasPassword": true,
    "channels": [
      { "channel": "telegram", "linked": true, "externalId": "4242001",
        "botUsername": "GetVoxlybot", "available": true },
      { "channel": "max", "linked": false, "externalId": null,
        "botUsername": "id505030516451_bot", "available": true }
    ]
  }
}
```

До появления этой группы данные о себе клиент получал только из ответа на вход
(`/auth/login`, `/auth/refresh`), поэтому менять их было нечем, а привязки
каналов и аватар вообще не покидали БД.

`hasPassword: false` у приглашённого сотрудника, который ещё не активировал
учётную запись — смена пароля для него недоступна. `available: false` означает,
что транспорт канала не настроен на сервере (нет токена бота), и привязка
невозможна.

## 13. `PATCH /api/v1/profile`

```json
{ "name": "Антон Проверкин", "phone": "+7 999 555 88 99", "avatar_url": "data:image/webp;base64,…" }
```

Все поля необязательны. `avatar_url: null` снимает аватар; отсутствие поля
оставляет его прежним — три состояния кодируются двумя SQL-параметрами, потому
что `COALESCE` не различает NULL-значение и отсутствие значения.

**E-mail изменить нельзя.** Он служит логином и адресом восстановления пароля,
поэтому смена требует подтверждения владения новым адресом — отдельного
сценария, которого пока нет. Молча позволить смену означало бы дать увести
учётную запись через профиль. Поле в интерфейсе показано как `disabled` с
объяснением.

Занятый в пределах арендатора телефон → `409 PHONE_TAKEN` с ошибкой поля
(частичный уникальный индекс из миграции 0008).

### Аватар: почему Base64

Загрузки файлов в проекте нет ни в каком виде — ни `@fastify/multipart`, ни
S3/MinIO, ни тома для медиа, ни раздачи статики. Выбран Base64 data-URI в
TEXT-колонке `users.avatar_url`:

- клиент (`frontend/src/lib/utils/avatar.ts`) центрально обрезает изображение до
  квадрата, масштабирует до **256×256** и кодирует в WebP с откатом на JPEG
  (Safari до 14 не кодирует WebP и молча вернул бы PNG втрое тяжелее);
- качество снижается ступенями `0.8 → 0.6 → 0.45`, пока результат не уложится в
  лимит;
- сервер проверяет **и** MIME, **и** фактический размер декодированных данных:
  заголовок data-URI задаёт клиент, доверять ему нельзя. Предел —
  `MAX_AVATAR_BYTES = 512 КБ`; практический результат 256×256 WebP — 15–35 КБ.
- SVG запрещён: он исполняет скрипты при рендере.

Проверено на живом стенде: PNG 1200×800 весом 622 КБ превращается в WebP 256×256
на 47 КБ data-URI. Это осознанный компромисс, а не незнание: он закрывает
сценарий «выбрать файл с диска» без новой инфраструктуры и переносится на
объектное хранилище заменой одного поля.

## 14. `POST /api/v1/profile/password` (лимит 10/мин)

```json
{ "current_password": "…", "password": "…8+ символов…", "keep_refresh_token": "…" }
```

Отличается от сброса по ссылке: там владение доказано письмом, здесь — знанием
действующего пароля. Без этой проверки перехваченная сессия позволяла бы сменить
пароль и закрепиться в учётной записи.

Отзываются все сессии, **кроме текущей**: смена пароля должна вытеснить того, кто
вошёл на другом устройстве, но выкидывать самого пользователя сразу после
успешного действия — потеря контекста без причины. Текущая исключается по хешу
её refresh-токена, который передаёт клиент в `keep_refresh_token`.

Ошибки: `401 INVALID_CURRENT_PASSWORD` (с ошибкой поля `current_password`),
`400 VALIDATION_ERROR` при совпадении нового с текущим,
`409 PASSWORD_NOT_SET` для неактивированного сотрудника.

## 15. Привязка каналов вошедшим пользователем

Раньше этого сценария не существовало: `AuthPurpose` был закрытым союзом
`register | login`, оба эндпоинта запроса кода публичны и не читают
`request.authUser`, а `requestCode` для `login` выводит телефон из e-mail.
Миграция `0009` добавила назначение `link`, колонку `auth_sessions.user_id` и
CHECK `auth_sessions_link_needs_user` — инвариант вместо обещания приложения:
сессия привязки обязана знать, кому привязывать.

### `POST /api/v1/profile/channels/:channel/link`

Возвращает тот же конверт, что `/auth/code/request`: `session_id`, `deep_link`,
`bot_username`, `expires_in_minutes`.

Два отличия от входа, оба существенные:

1. **Владелец берётся из токена,** а не из тела запроса — иначе можно было бы
   привязать канал к чужой учётной записи. Телефон читается с сервера по этому
   же идентификатору.
2. **Адресат по телефону не ищется.** Цель — привязать конкретный чат, а не
   воспользоваться чужой существующей привязкой, поэтому `deep_link` выдаётся
   всегда, и канал получит тот аккаунт, который её откроет.

`409 CHANNEL_ALREADY_LINKED`, если канал уже привязан.

### `POST /api/v1/profile/channels/verify` (лимит 20/мин)

```json
{ "session_id": "…", "code": "123456" }
```

Код обязателен, хотя пользователь уже аутентифицирован: без него достаточно было
бы открыть чужую ссылку, а код доказывает, что открывший владеет именно этим
чатом.

**Webhook по-прежнему не пишет в `users`** — это ключевое свойство, введённое в
предыдущей итерации и сохранённое здесь. `bindRecipient` записывает адресата
только в `auth_sessions`; в `users` он попадает исключительно из
`linkVerifiedRecipient` после проверки кода. Проверено на стенде: после
`bot_started` колонка пользователя остаётся `NULL`.

Гашение сессии выполняет `consumeLinkSession`, а не `consumeVerified`: та сверяет
телефон и e-mail, но у приглашённого сотрудника телефон может быть пустым, а
e-mail в `link`-сессии не хранится. Здесь строже — сверяется `user_id`, поэтому
сессию другого пользователя предъявить нельзя (`401 Код выдан для другой учётной
записи`).

`linkVerifiedRecipient` теперь возвращает исход
(`linked | already_linked | taken | skipped`) вместо `void`: для настроек нужно
различать «привязано» и «занято другой учётной записью». Второе даёт
`409 CHANNEL_TAKEN`. При входе исход игнорируется — вход уже состоялся, и
занятый чат не должен его ломать.

### `DELETE /api/v1/profile/channels/:channel`

Снимает привязку. `409 LAST_CHANNEL`, если это единственный привязанный канал:
код второго фактора доставляется только в бота, и учётная запись без привязок
осталась бы без способа войти. Отказ честнее неработающего входа; в интерфейсе
кнопка заблокирована с объяснением в подсказке.

`409 CHANNEL_NOT_LINKED`, если канал и так не привязан.

### `GET /api/v1/profile/channels/status?session_id=…`

Опрос доставки — тот же смысл, что публичный `/auth/code/status`. Нужен потому,
что код приходит уже после ответа на запрос ссылки, когда пользователь нажал
Start в боте.

## 17. Чего пока нет

- **Оплата.** Платёжный провайдер не подключён (`M5.2.6`, `M5.2.10`): нет
  привязки карты, автопродления, истории платежей и выставления счёта по ИНН.
  Страница `/settings/billing` показывает это явной подписью, а не имитацией
  работающей оплаты. Реквизитов самого арендатора (ИНН, КПП) в `tenants` нет.
- **Ограничение доступа по окончании триала** (`M0.11.9`) — списаний нет,
  поэтому доступ не сужается.
- **Права по отдельности.** Роль задаёт набор при создании; точечная выдача
  отдельного права через интерфейс не реализована.
- **Очистка просроченных приглашений** — та же задача `M0.8.12`, что для
  `auth_sessions` и `password_reset_tokens`.
- **Смена собственного e-mail** — требует подтверждения владения новым адресом
  (`M0.13.18`).
- **Аватар в объектном хранилище.** Base64 в TEXT работает, но картинка
  возвращается в каждом ответе профиля и не кэшируется браузером отдельно
  (`M0.13.19`).
