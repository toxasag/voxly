# 03_07 — AI API (агенты и баланс ИИ)

AI-агенты, баланс ИИ и наценка на токены.
Смонтировано в `app.ts` под `/api/v1/ai`.

> Источник: `backend/src/modules/ai/ai.routes.ts`, `ai.service.ts`, `ai.types.ts`,
> `ai-pricing.ts`, `backend/src/db/migrations/0014_ai_balance_and_agents.sql`.
> Создан 2026-08-23.

---

## 1. Права и гейты

| Операция | Право | Гейт модуля |
|---|---|---|
| Чтение агентов, каталог моделей | `ai_bots:read` | `ai_bots` |
| Создание, изменение, удаление | `ai_bots:configure` | `ai_bots` |
| Баланс ИИ и пополнение | `billing:manage` | нет |

Баланс намеренно **не закрыт** гейтом модуля: он виден в биллинге даже при
отключённом `ai_bots`, иначе арендатор не смог бы увидеть, за что с него списали.
Право `billing:manage` отделено от `ai_bots:configure` — настройка ботов не должна
давать возможность пополнять счёт.

---

## 2. Деньги хранятся в копейках

`ai_balance_kopecks`, `charged_kopecks`, `provider_cost_kopecks` — целые BIGINT.
`NUMERIC` с плавающей точкой недопустим: `0.1 + 0.2 ≠ 0.3`, и остаток баланса со
временем расходился бы с суммой операций. Наружу суммы отдаются в копейках
(`balanceKopecks`), принимаются в рублях (`amount_rubles`) — вводит их человек.

Прежняя `tenants.ai_tokens_balance` (остаток **в штуках токенов**) помечена
устаревшей и оставлена: на неё ссылаются платформенные экраны и контракт `03_04`.
Она не годится как основной счётчик — цена 1000 токенов различается между
моделями в десятки раз (DeepSeek 11 копеек против Opus 810), поэтому «остаток
токенов» не отвечает на вопрос, на сколько их хватит.

---

## 3. Тарификация

`ai-pricing.ts` — единственное место, где токены превращаются в деньги. Каталог
живёт на сервере, потому что цена служит основанием для списания, и клиент не
должен иметь возможности её задать.

```
providerCost = tokensIn/1000 × costInPer1k + tokensOut/1000 × costOutPer1k
charged      = ceil(providerCost × (1 + markupPercent/100))
```

Округление вверх выполняется на итоговой сумме, а не на промежуточных: иначе
тысячи вызовов по 0.4 копейки списывались бы как ноль, и расход был бы бесплатным
для арендатора при реальных затратах платформы.

Себестоимость и списанная сумма хранятся в `ai_usage_log` **обе**: по разнице
считается маржа, а пересчёт задним числом невозможен — наценку могли изменить
после вызова.

## 5. Агенты

### `GET /agents`

```json
{
  "data": [{
    "id": "ee706247-…", "name": "Квалификация лидов",
    "description": "Выясняет задачу и бюджет",
    "accent": "amber", "model": "gpt-4o-mini",
    "status": "active", "mode": "suggester",
    "temperature": 0.7, "maxTokens": 1024,
    "systemPrompt": "…", "contextEntities": ["contacts", "deals"],
    "tokensUsed": 0, "requestsCount": 0, "avgLatencyMs": 0, "spentKopecks": 0,
    "lastUsedAt": null,
    "createdAt": "2026-08-23T20:45:30.741Z", "updatedAt": "2026-08-23T20:45:30.741Z"
  }],
  "meta": { "total": 1 }
}
```

Агрегаты расхода подтягиваются одним запросом через `LEFT JOIN LATERAL`: отдельный
запрос на каждого агента был бы задачей N+1 — список из 20 агентов давал бы 21
обращение к БД.

**Лимита токенов на агента нет.** Расход ограничен общим балансом ИИ, поэтому поля
`tokens_limit` в ответе нет; интерфейс трактует 0 как «лимита нет».

### `POST /agents`

Обязательны `name`, `model`, `mode`, `status`, `accent`, `temperature`,
`max_tokens`, `system_prompt`. Ответ `201` с полным объектом агента.

| Код | HTTP | Причина |
|---|---|---|
| `AGENT_NAME_TAKEN` | 409 | имя занято (сравнение без учёта регистра) |
| `VALIDATION_ERROR` | 400 | неизвестная модель, короткий промпт, температура вне 0–1 |

Уникальность имени — частичный индекс `(tenant_id, lower(name)) WHERE deleted_at
IS NULL`: два агента «Продажи» в списке неразличимы, но удалённое имя можно
использовать снова.

Чтение созданной строки выполняется **вне** транзакции: `getAgent` берёт из пула
другое соединение и внутри `withTenant` не увидел бы ещё не зафиксированную
строку — запрос отвечал 404 на только что созданного агента (проверено).

### `PATCH /agents/:id`

Любое подмножество полей. Пустой объект отклоняется.

### `DELETE /agents/:id`

`204`. Мягкое удаление: `ai_usage_log` ссылается на агента и должен остаться
читаемым.

## 6. Баланс ИИ

### `GET /balance`

```json
{
  "data": {
    "balanceKopecks": 150000,
    "spentThisMonthKopecks": 0,
    "spentTotalKopecks": 0,
    "requestsThisMonth": 0,
    "markupPercent": 30,
    "estimatedTokensLeft": 8241758,
    "lastTopupAt": "2026-08-23T20:45:30.291Z"
  }
}
```

`estimatedTokensLeft` — оценка по GPT-4o mini, а не гарантия: интерфейсу нужно
ответить, надолго ли хватит суммы, но у разных моделей цена различается в десятки
раз.

### `POST /balance/topup`

```json
{ "amount_rubles": 1000 }
```

Минимум 100 ₽, максимум 500 000 ₽ за операцию (защита от опечатки на порядок).
Возвращает обновлённый баланс.

Платёжного провайдера в проекте нет: сумма зачисляется напрямую, операция
пишется в `ai_balance_topups` с `source = 'manual'` и в `tenant_audit_log`.
Интерфейс говорит об этом прямо — кнопка «Оплатить картой», ведущая в никуда, была
бы хуже честной подписи.

Инкремент выполняется в БД (`ai_balance_kopecks + $2`), а не чтением и записью в
приложении: два одновременных пополнения потеряли бы одно из них.

## 7. Наценка: `PATCH /api/v1/admin/tenants/:id`

Под `requirePlatformOwner` (см. `03_04`). Новые поля:

| Поле | Тип | Смысл |
|---|---|---|
| `ai_markup_percent` | number | наценка, % от цены провайдера |
| `ai_balance_rubles` | number | баланс ИИ в рублях (сервер переводит в копейки) |

Диапазон наценки −100…1000 %, проверяется в схеме Zod **и** `CHECK` в БД: запрос
можно отправить минуя интерфейс. Отрицательная наценка допустима как скидка, но
ниже −100 % цена стала бы отрицательной и расход пополнял бы баланс.

`GET /api/v1/admin/tenants` дополнительно отдаёт `ai_balance_kopecks`,
`ai_markup_percent` и `ai_spent_month_kopecks`.

## 8. База знаний агента (RAG)

Требует расширения `pgvector` — образ БД собирается из
`docker/postgres-pgvector.Dockerfile` (`postgres:16-alpine` + pgvector 0.8.0 из
исходников). Готового alpine-образа с расширением не существует, а переход на
Debian сменил бы libc и обесценил бы текстовые индексы существующего тома.

Права те же, что у самого агента: база знаний определяет его ответы, поэтому
право на её изменение равно праву на настройку (`ai_bots:configure`). Гейт модуля
`ai_bots` действует.

### `GET /agents/:id/knowledge`

```json
{
  "data": [
    {
      "id": "…uuid…",
      "agentId": "…uuid…",
      "filename": "Регламент СЦ.docx",
      "mimeType": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
      "fileSize": 20480,
      "status": "ready",
      "errorMessage": "",
      "chunksCount": 14,
      "createdAt": "2026-08-24T13:05:02.524Z"
    }
  ],
  "meta": {
    "total": 1,
    "vectorisationAvailable": true,
    "supportedExtensions": ["txt", "md", "docx", "pdf"],
    "maxFileSizeBytes": 10485760
  }
}
```

`status` — `processing` (текст извлечён, векторизация идёт), `ready`, `failed`
(причина в `errorMessage`). Документ не может оказаться `ready` без фрагментов:
статус переводится в той же транзакции, что и вставка векторов.

`vectorisationAvailable` приходит вместе со списком, а не отдельным запросом:
интерфейс обязан предупредить о ненастроенном на платформе доступе к моделям **до**
попытки загрузки, иначе пользователь узнаёт о нём только по ошибке.

Документы с `agentId: null` — общие для арендатора: они участвуют в поиске всех
агентов, поэтому регламент компании не нужно векторизовать по разу на агента.

Чужой или несуществующий агент — `404`, а не пустой список: иначе интерфейс по
неверному URL показывал бы «база знаний пуста» вместо «агент не найден».

### `POST /agents/:id/knowledge`

Два способа в одном маршруте, различаемых по `Content-Type`.

**Текстом** (`application/json`):

```json
{ "title": "Регламент сервисного центра", "text": "…до 500 000 символов…" }
```

**Файлом** (`multipart/form-data`, поле `file`): `txt`, `md`, `docx`, `pdf`,
не более **10 МБ**.

Тип определяется по расширению, а не по MIME из запроса: браузеры присылают
`application/octet-stream` для docx, а `curl` — что угодно. Файл, обрезанный по
лимиту, отклоняется с `413`, иначе в базу попал бы неполный документ, выглядящий
как успешно загруженный.

**Ответ `201`** — DTO документа с `chunksCount`.

Обработка: текст нормализуется (нулевой байт удаляется — PostgreSQL отклоняет его
в `TEXT`, а в pdf он встречается), режется на фрагменты **1000–1500 символов с
перекрытием 200**, разрез ищется по границе абзаца → предложения → пробела.
Перекрытие нужно потому, что ответ может лежать на стыке; разрез посреди
предложения лишает фрагмент подлежащего или отрицания, и его вектор перестаёт
соответствовать смыслу.

Векторизация идёт пачками по 32 фрагмента: вызов на каждый фрагмент дал бы сотни
round-trip'ов, а вся пачка целиком рисковала бы упереться в предел размера
запроса у шлюза.

**Ошибки:** `400 VALIDATION_ERROR`, `400 UNSUPPORTED_DOCUMENT_TYPE`,
`400 EMPTY_DOCUMENT` (скан без текстового слоя), `400 DOCUMENT_PARSE_FAILED`
(повреждённый или защищённый паролем файл), `404 NOT_FOUND`,
`413 FILE_TOO_LARGE`, `502 EMBEDDINGS_FAILED`, `503 EMBEDDINGS_UNAVAILABLE`.

`503` возвращается **до** создания документа: иначе в списке оставалась бы запись
со статусом `failed` там, где причина — конфигурация платформы, а не файл.

### `DELETE /agents/:id/knowledge/:docId`

**Ответ `204`.** Фрагменты уходят каскадом по `document_id`; удаление агента
каскадно удаляет всю его базу знаний.

### Семантический поиск

Внутренний, отдельного маршрута нет — используется перед вызовом модели:

```sql
SELECT ch.content, (ch.embedding <=> $4::vector) AS distance, ch.document_id, d.filename
FROM knowledge_base_chunks ch
JOIN knowledge_base_documents d ON d.id = ch.document_id
WHERE ch.tenant_id = $1
  AND (ch.agent_id = $2 OR ch.agent_id IS NULL)
  AND (ch.embedding <=> $4::vector) <= $3
ORDER BY distance ASC
LIMIT 4;
```

**Порог 0.75** подобран по измерениям на реальном регламенте
(`text-embedding-3-small`, вопросы на русском): по теме 0.35–0.65, не по теме
0.84–0.90. Порог обязателен — без него поиск всегда возвращает четыре фрагмента, и
модель получала бы случайный текст как «найденное в документах», то есть уверенно
выдумывала бы ответ. Первоначальные 0.6 отсекали валидный вопрос (0.648) и
заменены после замеров.

Размерность `vector(1536)` соответствует `text-embedding-3-small` (подтверждено
живым вызовом). Смена модели эмбеддингов требует миграции: векторы разной длины в
одной таблице несравнимы, и поиск молча возвращал бы мусор.

## 9. Привязка агента к аккаунтам каналов

### `GET /agents/:id/channels`

```json
{
  "data": [
    {
      "channelAccountId": "…uuid…",
      "channel": "telegram",
      "label": "Основной",
      "externalId": "@genadich_agency",
      "status": "connected",
      "isBound": true,
      "isEnabled": true
    }
  ],
  "meta": { "total": 1 }
}
```

Возвращаются **все** подключённые аккаунты арендатора с признаком привязки, а не
только привязанные: интерфейсу нужен список для выбора, и отдельный запрос за
«доступными» аккаунтами означал бы два источника одного списка.

### `PUT /agents/:id/channels`

```json
{ "channel_account_ids": ["…uuid…"] }
```

Заменяет набор **целиком**, а не добавляет по одному: интерфейс отправляет
итоговое состояние чекбоксов, а инкрементальные операции требовали бы от него
вычислять разницу — источник расхождений при редактировании из двух вкладок.
Замена выполняется одной транзакцией: между двумя отдельными запросами агент
оказался бы без каналов, и входящее сообщение в этот момент осталось бы без
ответа.

Принадлежность каждого аккаунта арендатору проверяется на сервере и даёт `404`
с понятным текстом — RLS отклонила бы чужой идентификатор ошибкой БД, но
невнятной. Дубликаты в запросе схлопываются: повтор не должен нарушать первичный
ключ `(agent_id, channel_account_id)`. Удаление аккаунта канала снимает привязку
каскадом.

**Ответ `200`** — обновлённый список в том же формате, что у `GET`.

## 10. Требования к окружению

| Переменная | По умолчанию | Примечание |
|---|---|---|
| `LLM_API_BASE_URL` | — | OpenAI-совместимый шлюз; задаётся вместе с ключом |
| `LLM_API_KEY` | — | без пары «адрес + ключ» база знаний отвечает `503 EMBEDDINGS_UNAVAILABLE` |
| `LLM_EMBEDDING_MODEL` | `openrouter/openai/text-embedding-3-small` | размерность обязана совпадать с `vector(1536)`; смена требует миграции |

Один адрес и один ключ на все модели вместо ключа на провайдера: иначе каждая
новая модель в каталоге означала бы новую переменную окружения. Валидация требует
пару целиком — с одним из двух вызов упал бы `401` у провайдера, то есть база
знаний ломалась бы в рантайме вместо честного отказа на старте.

## 11. Автоответы в мессенджерах (M7.5.16, M4.2.18, M4.2.19)

Не HTTP-эндпоинт: агент отвечает на сообщения, приходящие в подключённый аккаунт
канала. Описано здесь, потому что расходует баланс ИИ и пишет `ai_usage_log`.

### Условия, при которых агент отвечает

Все три обязательны:

1. аккаунт канала подключён (`channel_accounts.status = 'connected'`) и к нему
   привязан агент (`ai_agent_channel_bindings.is_enabled`);
2. агент активен и в режиме автоответа (`status = 'active'`,
   `mode = 'autoreply'`). В режиме `suggester` агент молчит: черновики
   предназначены оператору, и отправка их клиенту игнорировала бы настройку;
3. на балансе не меньше **100 копеек**. Порог нужен потому, что стоимость известна
   только после ответа модели: без предварительной проверки арендатор уходил бы в
   минус на каждом сообщении.

При нескольких агентах на одном аккаунте отвечает старейший по `created_at`:
одновременный ответ двух агентов означал бы два разных ответа на одно сообщение.

### Что игнорируется

Групповые чаты и каналы, собственные исходящие сообщения (иначе агент отвечал бы
на свои же реплики и диалог зациклился бы) и медиа без текстовой подписи —
распознавание голоса и изображений не реализовано, а ответ «не понял» на
голосовое хуже молчания оператора.

### Дебаунс

Сообщения одного диалога накапливаются **15–20 секунд** (случайное значение:
фиксированная пауза читается как автоответчик) и уходят в модель одним текстом,
склеенным через `\n`. Человек пишет очередями коротких реплик, и ответ на каждую
означал бы три вызова модели, три списания и три несвязных ответа.

Ключ буфера — пара «аккаунт + chat_id»: один и тот же `chat_id` у двух аккаунтов
это разные диалоги.

Два предела сверх задания:

| Предел | Значение | Зачем |
|---|---|---|
| Жёсткий дедлайн от первого сообщения | 60 с | клиент, который печатает не останавливаясь, продлевал бы окно бесконечно и не получил бы ответа никогда |
| Размер пачки | 30 сообщений / 8000 символов | иначе промпт растёт без границы; отброшенные сообщения попадают в лог, а не исчезают молча |

Буфер живёт в памяти процесса. Redis не используется: буфер осмыслен только вместе
с MTProto-соединением в том же процессе, и при падении контейнера восстанавливать
его некуда — клиент напишет снова.

### Формат ответа модели

Модель обязана вернуть строгий JSON:

```json
{ "message1": "Первое короткое предложение", "message2": "Второе с вопросом", "message3": "" }
```

Разбор свободного текста по пустым строкам ломался бы на любом списке в ответе.
JSON извлекается и из markdown-блока, и из ответа с предисловием — модели
оборачивают его даже при `response_format: json_object`. Читаются строго ключи
`message1..3`: посторонние поля вроде `reasoning` не должны уйти клиенту.

Непригодный ответ означает **молчание**: отправить сырой JSON или «извините,
ошибка» от имени компании хуже, чем оставить диалог оператору. Расход при этом
списывается — токены провайдер уже потратил.

### Отправка

`SetTyping` → пауза → сообщение, для каждого из сообщений. Пауза между
сообщениями **2.5–4.5 секунды** (случайная), перед первым — 1.2 с: мгновенный
ответ после 15 секунд тишины выглядит как автоответчик.

Статус «печатает» ставится перед каждым сообщением, а не один раз: Telegram гасит
его через ~5 секунд, и при паузе до 4.5 с он успевал бы исчезнуть.

Ошибка отправки прерывает остаток пачки: если Telegram отклонил первую реплику
(блокировка, flood wait), остальные тем более не уйдут, а попытки продлили бы
ограничение.

### Списание и журнал

Списание с `tenants.ai_balance_kopecks` и запись в `ai_usage_log` выполняются в
**одной транзакции**: иначе возможны обе половины по отдельности — расход, который
нельзя объяснить, или бесплатное пользование. Наценка читается внутри транзакции
(`FOR UPDATE` на арендаторе): между проверкой баланса и списанием её могли
изменить.

`GREATEST(ai_balance_kopecks - N, 0)` не даёт остатку стать отрицательным: разница
— потеря платформы, и она предпочтительнее долга, показанного в интерфейсе.

`user_id` в журнале — NULL: вызов инициирован клиентом из мессенджера, а не
сотрудником.

| Ситуация | Журнал | Списание |
|---|---|---|
| Ответ отправлен | `success` | да |
| Ответ вне формата JSON | `error`, причина в `error_message` | да — токены потрачены |
| Отказ вызова (таймаут, 5xx) | `error` | нет — токенов не было |
| Нет агента, пауза, малый баланс, нет доступа к моделям | не пишется | нет |

### Ограничение по репликам

Слушатель поднимается в каждом процессе бэкенда. При нескольких репликах каждая
подписалась бы на те же аккаунты, и клиент получил бы по ответу от каждой. Сейчас
бэкенд запускается одним контейнером; при масштабировании понадобится блокировка
(`M4.2.20`).

## 12. Чего пока нет

**Переписка не сохраняется** (`M7.5.18`). Транспорт обрабатывает входящие и
отвечает, но ни сообщения клиента, ни ответы агента никуда не пишутся: оператор не
видит диалог в CRM, а контекст модели ограничен одной пачкой — предыдущие
сообщения диалога в промпт не попадают.

**Потокового чата в интерфейсе** (`M4.2.4`). Пробный чат на странице агента
работает на локальной имитации и помечен как демонстрационный. Для реальных
ответов нужен SSE-эндпоинт и `streamChat` в абстракции провайдера; сама абстракция
и поиск по базе знаний уже готовы и используются транспортом.

**Контекстных переменных** (`M4.2.7`): `{{contact}}`, `{{deal}}` не подставляются —
в промпт идут только фрагменты базы знаний.

**Повторной векторизации** при смене модели эмбеддингов: исходный текст для этого
сохраняется в `knowledge_base_documents.content_text`, но маршрута нет.

**Работающего ключа шлюза.** На момент деплоя ключ упёрся в лимит OpenRouter: все
13 моделей эмбеддингов отвечают `403`, chat доступен только через `auto/*`.
Загрузка документов и ответы агента заработают после пополнения — изменений в коде
не требуется.
