## 1. Базовый путь

```
/auth
```

> Расхождение с реестром: маршруты смонтированы под `/auth`, а не `/api/v1/auth` (`backend/src/app.ts`). Ниже описано фактическое состояние. Приведение к `/api/v1/auth` потребует правки `app.ts` и списка публичных путей в `authenticate.ts`.

Все эндпоинты группы публичные — они входят в `PUBLIC_PATHS` и не требуют токена: они либо выдают учётные данные, либо вызываются платформами ботов, либо восстанавливают доступ, когда войти нельзя по определению.

## 2. Статус реализации

Выдача токенов работает на реальных данных. Заглушки `temp-user-id` / `temp-tenant-id` удалены: `sub` и `tenant_id` берутся из таблиц `users` и `tenants`, коды OTP хранятся в `otp_codes` как argon2-хеши, refresh-токены — в `refresh_tokens` как SHA-256-дайджесты с ротацией.

Коды подтверждения доставляются ботами Telegram и MAX (§4.3). Восстановление пароля работает через SMTP (§7.1–7.2). Просроченные строки аутентификации очищаются по расписанию (§15).

Контур покрыт интеграционными тестами (`backend/src/tests/`, 77 тестов): вход по паролю и с кодом, регистрация, ротация refresh, восстановление пароля, приглашения, изоляция арендаторов, гейты модулей и прав, очистка. Запуск — `npm test` в `backend/`.

Тестовая база подключается непривилегированной ролью `getvoxly_test_app_user` — отдельной от рабочей `app_user` и с теми же флагами (`NOSUPERUSER NOBYPASSRLS NOINHERIT`). Имя обязано отличаться: `ALTER ROLE` действует на весь кластер, и прогон тестов под именем рабочей роли менял бы ей пароль. Подстановка `app_user` через `TEST_APP_ROLE` отклоняется.

Открытые задачи: `M0.6.2` (доставка через SMS/WhatsApp; устаревший `POST /auth/otp/send` по-прежнему пишет код в лог на уровне `debug`), `M0.6.5` (httpOnly-cookie; сейчас токены возвращаются в теле ответа), `M0.8.13` (обязательный второй фактор), `M0.12.9`–`M0.12.10` (сопоставление ошибок с полями формы, тупик `awaiting_bot`).

## 3. Модель токенов

| Параметр | Значение |
|---|---|
| Библиотека | `@fastify/jwt` |
| Секрет | `JWT_SECRET` из валидированного окружения (`config/env.ts`) |
| Срок access-токена | `ACCESS_TOKEN_TTL`, по умолчанию 15 минут |
| Обязательные поля | `sub` (id пользователя), `tenant_id` |
| Дополнительные поля | `role`, `typ` |
| Refresh-токен | 48 случайных байт (`base64url`), не JWT |
| Срок refresh-токена | `REFRESH_TOKEN_TTL_DAYS`, по умолчанию 30 дней |

Поле `typ` разделяет назначение токенов: `access` допускается на защищённых маршрутах, любое другое значение отклоняется с `401 UNAUTHORIZED` («Invalid token type»). Токены без `typ` принимаются как access для обратной совместимости.

Refresh-токены в БД хранятся только в виде хеша, поэтому дамп таблицы нельзя переиграть как вход.

Access-токен передаётся в заголовке:

```
Authorization: Bearer <jwt>
```

## 4. Общий формат успешного ответа

`otp/verify`, `login`, `refresh` и `register` возвращают одинаковую структуру:

```json
{
  "data": {
    "access_token": "<jwt>",
    "refresh_token": "<opaque>",
    "token_type": "Bearer",
    "expires_in": "15m",
    "user": {
      "id": "…uuid…",
      "name": "Иван Петров",
      "email": "ivan@acme-corp.com",
      "phone": "+79991234567",
      "role": "owner",
      "permissions": ["contacts:read", "…"]
    },
    "tenant": {
      "id": "…uuid…",
      "name": "Acme Corp",
      "slug": "acme",
      "plan": "enterprise",
      "status": "active"
    }
  }
}
```

Профиль и арендатор отдаются сразу, чтобы клиенту не требовался отдельный запрос для инициализации контекста. Значения `permissions`, отсутствующие в модели прав, отбрасываются при чтении.

`tenant.slug` — личный поддомен арендатора (`{slug}.getvoxly.ru`). Frontend использует его, чтобы после входа перевести пользователя на его портал, и чтобы вернуть его туда при открытии чужого поддомена.

## 4.1. `POST /auth/register`

Публичная регистрация: создаёт арендатора, его поддомен и владельца, затем сразу выдаёт токены. Аутентификация не требуется.

**Запрос**

```json
{
  "company_name": "ООО Ромашка",
  "slug": "romashka",
  "owner_name": "Мария Смирнова",
  "email": "maria@romashka.ru",
  "phone": "+7 921 000 55 66",
  "password": "…минимум 8 символов…"
}
```

**Ответ** — `201` с конвертом из §4. Владелец получает роль `owner` и полный набор из 19 прав; арендатор создаётся в плане `trial` со статусом `trial`.

**Ошибки**

| Код | Статус | Причина |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Поддомен занят, зарезервирован или имеет недопустимый формат; e-mail уже зарегистрирован. Сообщения приходят в `details` по имени поля |
| `SLUG_TAKEN` | 409 | Поддомен занят между проверкой и вставкой (гонка двух регистраций) |

Арендатор и владелец создаются в одной транзакции: арендатор без владельца недоступен, а владельцу без арендатора нельзя выдать токен. Уникальность поддомена гарантирует индекс в БД, а не предварительная проверка.

E-mail уникален в пределах платформы, а не арендатора: он служит идентификатором для входа по паролю, у которого нет tenant-контекста.

## 4.2. `GET /auth/slug-available`

Проверка занятости поддомена для формы регистрации. Аутентификация не требуется.

`GET /auth/slug-available?slug=romashka`

```json
{ "data": { "slug": "romashka", "available": true, "reason": null } }
```

`reason` принимает значения `TAKEN`, `RESERVED`, `INVALID_FORMAT` либо `null`.

Проверка **рекомендательная**: две регистрации могут пройти её одновременно, и конфликт разрешает уникальный индекс `idx_tenants_slug`. Клиент обязан обрабатывать `SLUG_TAKEN` при отправке формы.

### Формат поддомена

Метка DNS: строчная латиница, цифры и дефис, 3–63 символа, не начинается и не заканчивается дефисом. Правило продублировано в трёх местах, потому что значение попадает в имя хоста: Zod-схема на клиенте, Zod на сервере и CHECK-ограничение `tenants_slug_format` в БД.

Служебные имена (`api`, `app`, `www`, `admin`, `superadmin`, `n8n`, `baserow` и другие — всего 32) лежат в таблице `reserved_slugs` и недоступны арендаторам.

## 4.3. Подтверждение через бота (@GetVoxlybot в Telegram, @id505030516451_bot в MAX)

Регистрация и вход подтверждаются 6-значным кодом, который доставляет бот. Код живёт `OTP_TTL_MINUTES` (по умолчанию 5 минут) и хранится только как argon2-хеш.

Состояние подтверждения лежит в таблице `auth_sessions`, а не в памяти процесса: при перезапуске контейнера все ожидающие сессии обнулились бы. Redis в стек не развёрнут.

### `POST /auth/code/request`

Лимит **5 запросов в минуту на IP** — строже общего (100/мин), поскольку каждый вызов отправляет сообщение в чужой Telegram-чат.

```json
{ "purpose": "register", "channel": "telegram", "phone": "+7 921 000 55 66", "email": "owner@company.ru" }
```

`purpose` — `register` либо `login`. Для `register` обязателен `phone`; для `login` обязателен `email`, а телефон резолвится по нему на сервере (форма входа его не спрашивает).

`channel` — `telegram` либо `max`. Оба транспорта подключены; `503 MAX_UNAVAILABLE` возвращается только когда не задан `MAX_BOT_TOKEN` (симметрично `503 TELEGRAM_UNAVAILABLE`). Канал — параметр всего пути, а не ветка: адресат берётся из `users.telegram_chat_id` либо `users.max_user_id`, и дальше сценарий одинаков.

### Как резолвится адресат (изменено 2026-08-24, `M0.12.6`)

Ключ резолва — **e-mail**, и адресат читается из той же строки `users`, что и телефон.

Прежние незавершённые сессии того же назначения гасятся по `user_id`, а не по телефону — для `login` и `link`, где пользователь известен. Телефон для этого негоден по той же причине, по которой негоден для резолва: он уникален только внутри арендатора, и гашение по номеру снимало непогашенную сессию входа однофамильца из другой компании. У `register` пользователя ещё нет, поэтому там ключом остаётся номер; двум арендаторам он в этот момент не принадлежит.

Сверка при потреблении сессии (`consumeVerified`) идёт по `user_id`, когда он известен обеим сторонам, и только иначе — по номеру. Это строже (идентификатор уникален глобально) и не отказывает пользователю без телефона: у него в сессии стоит заглушка `unknown-…`, с которой сравнение по номеру не совпало бы никогда. Несовпадение владельца даёт `401` «Код выдан для другой учётной записи».

Прежняя версия искала адресата по номеру телефона среди всех арендаторов. `UNIQUE (tenant_id, phone)` действует внутри арендатора, поэтому один номер законно существует у сотрудников разных компаний, а выборка брала первую строку по `created_at`: при совпадении номера код входа уходил в чат чужого аккаунта, и его владелец получал сообщение о входе, которого не совершал. Чтение телефона и адресата из одной строки делает расхождение «телефон одного, чат другого» невозможным по построению.

Отбор совпадает с выборками входа (`deleted_at IS NULL AND activated_at IS NOT NULL`, общий предикат `activeUserPredicate()`): иначе удалённый или ещё не активированный однофамилец перехватывал бы выборку, а войти всё равно не мог.

`purpose: "register"` **всегда** идёт через deep-link: учётной записи ещё нет, законной существующей привязки быть не может. Прежний поиск по номеру был и тупиковым — `idx_users_telegram_chat_id` уникален, поэтому перенос чужого чата на создаваемого владельца завершался `409 TELEGRAM_ALREADY_LINKED` уже после погашения кода.

**Ответ**

```json
{
  "data": {
    "session_id": "…uuid…",
    "channel": "telegram",
    "delivered": false,
    "deep_link": "https://t.me/GetVoxlybot?start=auth_<token>",
    "bot_username": "GetVoxlybot",
    "expires_in_minutes": 5
  }
}
```

Для MAX `deep_link` имеет вид `https://max.ru/id505030516451_bot?start=auth_<token>`, а `bot_username` — `id505030516451_bot`.

Два сценария:

- **адресат известен** (пользователь уже привязывал канал) — код уходит в чат сразу, `delivered: true`, `deep_link: null`.
- **адресат неизвестен** — код **не генерируется**, отправлять его некуда. Возвращается `deep_link`; после `/start` бот привязывает чат и присылает код. Генерировать код заранее означало бы расходовать попытки на код, который никуда не ушёл.

**Известное ограничение: ответ различает известный и неизвестный e-mail.** Из двух сценариев выше следует, что адрес с уже привязанным ботом отвечает `delivered: true` без ссылки, а неизвестный — `delivered: false` со ссылкой. Заглушка вместо телефона скрывает личность в хранимой строке, но не выравнивает ответ, поэтому эндпоинт остаётся оракулом существования для пользователей, привязавших канал; лимит 5/мин ограничивает скорость перебора, но не сам сигнал. Устранение потребовало бы всегда возвращать deep-link и сообщать доставку только через `/auth/code/status` (где нужен `session_id`) — это меняет поток в интерфейсе и вынесено отдельной задачей.

Если платформа отказала в доставке (бот заблокирован, чат удалён), привязка сессии сбрасывается и возвращается `deep_link` — иначе пользователь ждал бы код, которого не будет.

Отказ доставки **сразу после `/start`** откатывает шаг привязки целиком: снимаются адресат, `code_hash` и `delivered_at`, а deep-link токен возвращается **тот же**, поэтому уже показанная в браузере ссылка продолжает работать. Прежде сбрасывался только `delivered_at`: `code_hash` оставался при погашенной ссылке, и `verifyCode` списывал попытки за код, которого пользователь не получал (пять попыток гасили сессию), а повторный «Start» ничего не находил (`M0.12.7`).

Токен deep-link привязан к каналу: сессия ищется по паре «токен + канал», поэтому ссылку, выданную для Telegram, нельзя предъявить MAX-боту и наоборот.

### `GET /auth/code/status?session_id=…`

```json
{ "data": { "delivered": true, "verified": false, "expired": false } }
```

Нужен потому, что при первой привязке код отправляется **после** ответа на `/code/request` — в момент нажатия Start. Без опроса поле ввода кода оставалось бы заблокированным до перезагрузки страницы.

### `POST /auth/telegram/webhook`

Вызывается Telegram. Защищён секретом `TELEGRAM_WEBHOOK_SECRET`, который сверяется с заголовком `X-Telegram-Bot-Api-Secret-Token`; без совпадения — `401`. Без этой проверки любой, кто узнает URL, мог бы привязать произвольный `chat_id` к сессии подтверждения.

Обрабатывается только `/start`:

- `/start auth_<token>` — привязка чата к сессии и немедленная отправка кода. Токен гасится сразу, поэтому повторный переход по той же ссылке кода не выдаст.
- `/start` без токена — приветствие.

Некорректные обновления получают `200`: Telegram повторяет доставку при не-2xx, а повторять разбор битого апдейта бессмысленно. Эндпоинт исключён из общего rate limit — иначе всплеск обновлений отбрасывался бы и привязка молча ломалась.

Адрес webhook регистрируется автоматически при старте сервера (`PUBLIC_API_URL` + `/auth/telegram/webhook`). Это не косметика: у бота был прописан адрес удалённого легаси-стека, отдающий `404`, и Telegram доставлял обновления в никуда.

### `POST /auth/max/webhook`

Вызывается платформой MAX. Защищён секретом `MAX_WEBHOOK_SECRET`, который сверяется с заголовком `X-Max-Bot-Api-Secret`; без совпадения — `401`.

Секрет **обязателен**, а не «проверяется, если задан»: отсутствие ожидаемого значения трактуется как отказ. Пропуск проверки при пустом секрете сделал бы публичный эндпоинт открытым для подделки обновлений — любой, кто узнает URL, привязал бы произвольный аккаунт к сессии подтверждения. Обязательность обеспечивается на двух уровнях: `config/env.ts` не даёт серверу подняться, если задан `MAX_BOT_TOKEN` без `MAX_WEBHOOK_SECRET`, а обработчик всё равно отвечает `401`, если секрет почему-то отсутствует. Сравнение constant-time (`AuthService.safeEqual`): заголовок подконтролен вызывающему, и посимвольный выход раскрывал бы секрет по времени ответа. То же правило действует для `/auth/telegram/webhook`.

Структура обновления отличается от Telegram (объект [`Update`](https://dev.max.ru/docs-api/objects/Update)), поэтому разбирается отдельной схемой:

| Что | Telegram | MAX |
|---|---|---|
| Тип события | — | `update_type` (`bot_started`, `message_created`) |
| Отправитель | `message.chat.id` | `user.user_id` либо `message.sender.user_id` |
| Токен привязки | `message.text` = `/start auth_<token>` | `payload` = `auth_<token>`, либо текст `message.body.text` |
| Секрет | `X-Telegram-Bot-Api-Secret-Token` | `X-Max-Bot-Api-Secret` |

Основной путь привязки — событие `bot_started`: платформа передаёт в `payload` всё, что стояло после `?start=`. Разбор текста сообщения оставлен дополнительно, потому что клиент может отправить `/start auth_<token>` обычным сообщением.

### Когда адресат запоминается у пользователя

`/start` привязывает адресата **только к сессии подтверждения**, но не к строке в `users`. В этот момент известно лишь то, что кто-то открыл бота по ссылке: ни телефон, ни e-mail сессии ещё не подтверждены — оба свободно задаются вызывающим `/auth/code/request`.

`users.telegram_chat_id` / `users.max_user_id` заполняются в двух местах, и оба требуют доказанного владения аккаунтом:

- **успешный `POST /auth/login/verify`** — предъявлены и пароль, и код из чата (`linkVerifiedRecipient`, обновление по `users.id`);
- **`POST /auth/register`** — адресат переносится из подтверждённой сессии на создаваемого владельца (`verifiedRecipient`).

Это не косметика. Прежняя версия записывала адресата по совпадению одного номера телефона для любой сессии, включая `register`, поэтому достаточно было знать чужой номер: запросить код на регистрацию, открыть deep-link своим ботом — и привязка жертвы указывала бы на чужой чат, куда затем уходили её коды входа. Условие «колонка пуста» от этого не защищало: у ещё не привязанного пользователя она как раз пуста.

Вторая половина того же дефекта — резолв адресата **при выдаче** кода — закрыта 2026-08-24 переходом на ключ e-mail (см. «Как резолвится адресат» выше).

Некорректные обновления получают `200` по той же причине, что и у Telegram.

Оба webhook исключены из **общего** лимита (100/мин на IP), но не остаются безлимитными: у каждого свой потолок 600/мин. Полное отсутствие лимита на публичном обработчике, выполняющем запись в БД, дало бы неаутентифицированному вызывающему неограниченный путь записи. Выбранный потолок заведомо выше реального трафика бота — MAX держит не более 30 rps на весь домен. Исключение сверяется по точному пути, а не по префиксу: `startsWith` освобождал бы и произвольные суффиксы вида `/auth/max/webhookX`.

Ограничение общего лимита для этих путей необходимо: платформы повторяют недоставленное обновление, а MAX выполняет до 10 повторов с растущим интервалом и **автоматически отписывает бота**, если endpoint не отвечает успехом 8 часов.

Подписка создаётся при каждом старте сервера (`POST /subscriptions` с `update_types: ["bot_started", "message_created"]`), а не однократно — иначе после длительного простоя канал остался бы отключённым. Платформа принимает только HTTPS на порту 443; при `PUBLIC_API_URL` на `http` регистрация пропускается с ошибкой в логе.

### Отличия транспорта MAX от Telegram Bot API

Учтены в `services/max.service.ts`; из-за них сервис не является копией `telegram.service.ts`:

| Аспект | Значение |
|---|---|
| База | `https://platform-api2.max.ru` (не `platform-api.max.ru`) |
| Авторизация | заголовок `Authorization: <token>`; передача через query не поддерживается |
| Отправка | `POST /messages?user_id=<id>`, адресат в query, а не в теле |
| Разметка | `format: "html"` вместо `parse_mode` |
| Результат | по HTTP-коду: конверта `ok` у MAX нет |
| Лимиты | 30 rps на домен, не более 2 сообщений в секунду в один диалог |

### `POST /auth/register` — с подтверждением

К полям из §4.1 добавлены `session_id` и `code`; поля `company_name` и `owner_name` **удалены** — название арендатора выводится из `slug`, имя владельца из локальной части e-mail.

Код проверяется **до** создания арендатора, поэтому неподтверждённый номер не может занять поддомен. Сессия сверяется по `purpose`, `phone` и `email`: иначе подтверждённую сессию можно было бы предъявить для регистрации на другой номер.

**Код не расходуется при ошибке формы** (изменено 2026-08-24, `M0.12.8`). Гашение сессии выполняется внутри той же транзакции, что и создание арендатора, поэтому при `400 VALIDATION_ERROR` (занятый или зарезервированный поддомен, занятый e-mail), `409 SLUG_TAKEN`, `409 TELEGRAM_ALREADY_LINKED` и `409 MAX_ALREADY_LINKED` оно откатывается вместе с ошибкой: **тот же `session_id` и тот же `code` можно предъявить повторно**, исправив поле. Прежде код гасился до вставок, и правка одного поля требовала нового кода с повторным открытием бота.

Защита от повторного использования не ослабла: строка сессии берётся под `FOR UPDATE`, поэтому две одновременные регистрации по одному коду сериализуются, и второй запрос получает `401` «Код уже использован», а не второго арендатора. После успешной регистрации код погашен окончательно.

### `POST /auth/login/verify` — вход с кодом

```json
{ "email": "owner@company.ru", "password": "…", "session_id": "…uuid…", "code": "123456" }
```

Пароль проверяется **первым**, тем же кодом, что и обычный вход: код не должен служить заменой пароля. Только после успешной проверки пароля код сверяется и гасится. Ответ — конверт из §4.

`POST /auth/login` (без кода) остаётся доступен: его использует восстановление сессии и обратная совместимость. Обязательным второй фактор пока не является.

## 5. `POST /auth/otp/send`

Запрос кода подтверждения.

**Запрос**

```json
{ "phone": "+79991234567" }
```

| Поле | Тип | Правило |
|---|---|---|
| `phone` | string | 10–20 символов, обязательно |

**Ответ `200`**

```json
{ "data": { "message": "OTP sent", "expires_in_minutes": 5 } }
```

Поведение:

- телефон нормализуется до цифр, поэтому `+7 999 123 45 67` и `+79991234567` разрешаются в одного пользователя;
- ответ **одинаков** для известного и неизвестного номера — эндпоинт нельзя использовать для перебора пользователей. Для неизвестного номера код не генерируется и строка не пишется;
- предыдущие невыданные коды этого телефона гасятся (`consumed_at = now()`), поэтому активен всегда максимум один;
- код генерируется `crypto.randomInt` и сохраняется только как argon2-хеш.

**Ошибки:** `400 VALIDATION_ERROR`.

## 6. `POST /auth/otp/verify`

Проверка кода и выдача пары токенов.

**Запрос**

```json
{ "phone": "+79991234567", "code": "123456" }
```

| Поле | Тип | Правило |
|---|---|---|
| `phone` | string | 10–20 символов |
| `code` | string | ровно 6 цифр |

**Ответ `200`** — структура из §4.

Проверки выполняются в одной транзакции, выборка кода идёт под `FOR UPDATE`, поэтому счётчик попыток нельзя обойти параллельными запросами:

1. превышение `OTP_MAX_ATTEMPTS` (по умолчанию 5) — код гасится, `429 OTP_ATTEMPTS_EXCEEDED`;
2. истёкший срок — код гасится, `401 UNAUTHORIZED` («Code has expired»);
3. неверный код — счётчик попыток увеличивается, `401 UNAUTHORIZED`;
4. успех — код гасится (одноразовый) и в той же транзакции выдаются токены.

**Ошибки:** `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 TENANT_INACTIVE`, `429 OTP_ATTEMPTS_EXCEEDED`.

### Лимит попыток фактически не действовал до 2026-08-24 (`M0.12.15`)

Пункты 1–3 выше описывали намерение, но не поведение. Записи выполнялись внутри транзакции, из тела которой затем бросалось исключение, а `transaction()` в этом случае делает `ROLLBACK` — поэтому инкремент `attempts` и гашение исчерпанной сессии не сохранялись. Практическое следствие: `OTP_MAX_ATTEMPTS` не срабатывал **никогда**, и шестизначный код можно было подбирать без ограничения. Дефект был одинаков в `/auth/otp/verify`, `/auth/login/verify` (через `verifyCode`) и `/auth/refresh`.

Исправление: исход покидает транзакцию значением, ошибка формируется после коммита. `FOR UPDATE` сохранён, поэтому сериализация параллельных проверок работает как описано. Закреплено интеграционными тестами.

Вход по e-mail и паролю.

**Запрос**

```json
{ "email": "ivan@acme-corp.com", "password": "…" }
```

## 7.1. `POST /auth/forgot-password`

Запрос ссылки восстановления пароля. Аутентификация не требуется.

Лимит **5 запросов в минуту на IP** — строже общего: каждый вызов отправляет письмо.

**Запрос**

```json
{ "email": "owner@company.ru" }
```

**Ответ `200`**

```json
{ "data": { "message": "Если такой e-mail зарегистрирован, ссылка для восстановления отправлена." } }
```

Ответ **идентичен** для известного и неизвестного адреса, включая случай отказа SMTP: иначе эндпоинт стал бы инструментом проверки, зарегистрирован ли e-mail. Для неизвестного адреса строка не пишется и письмо не отправляется; сбой отправки только логируется.

**Отправка не ожидается** (изменено 2026-08-24, `M0.12.11`). Тело ответа было одинаковым и прежде, но время — нет: для известного адреса запрос ждал SMTP-обмен (сотни миллисекунд у внешнего провайдера, секунды таймаута при недоступности), для неизвестного возвращался сразу. Разница измерима с клиента, поэтому единый текст ничего не скрывал. Теперь ответ уходит, не дожидаясь письма.

Разрыв устранён не полностью: известный адрес по-прежнему выполняет транзакцию записи токена — единицы миллисекунд против одного `SELECT`. Убран именно сетевой обмен с внешним сервисом. Полное выравнивание потребовало бы фиктивных записей для неизвестных адресов, то есть роста таблицы от чужого перебора.

Токен — 32 случайных байта (`base64url`), в БД хранится только его SHA-256 (`password_reset_tokens.token_hash`), поэтому дамп таблицы нельзя переиграть как переход по ссылке. Срок жизни — **60 минут**. Прежние невыданные ссылки того же пользователя гасятся, поэтому активной остаётся ровно одна.

Ссылка в письме: `{PUBLIC_APP_URL}/reset-password?token=<token>`.

**Ошибки:** `400 VALIDATION_ERROR`, `429` при превышении лимита.

## 7.2. `POST /auth/reset-password`

Смена пароля по токену из письма. Аутентификация не требуется — в этом смысл ссылки.

Лимит **10 запросов в минуту на IP**: эндпоинт принимает токен, и общий лимит 100/мин оставлял бы слишком широкое окно.

**Запрос**

```json
{ "token": "<из ссылки>", "password": "…минимум 8 символов…" }
```

**Ответ `200`**

```json
{ "data": { "message": "Пароль обновлён. Войдите с новым паролем." } }
```

В одной транзакции, строка под `FOR UPDATE` (иначе два параллельных перехода по одной ссылке оба увидели бы непогашенный токен):

1. токен ищется по хешу; отсутствующий, погашенный или просроченный — `400 INVALID_RESET_TOKEN`;
2. `users.password_hash` перезаписывается новым argon2id-хешем;
3. токен гасится (`consumed_at`) — ссылка одноразовая;
4. **все активные refresh-токены пользователя отзываются.** Сброс пароля используют и когда доступ считают скомпрометированным, а уцелевшая сессия обесценила бы смену.

**Ошибки:** `400 VALIDATION_ERROR`, `400 INVALID_RESET_TOKEN`, `429`.

## 8. `POST /auth/refresh`

Обновление пары токенов с ротацией.

**Запрос**

```json
{ "refresh_token": "<token>" }
```

**Ответ `200`** — структура из §4, с новым `refresh_token`.

Логика (в одной транзакции, строка под `FOR UPDATE`):

- предъявленный токен отзывается (`revoked_at`), новый связывается с ним через `replaced_by`;
- повторное предъявление уже отозванного токена трактуется как признак утечки и отзывает **все** активные сессии пользователя, после чего возвращает `401`;
- истёкший токен — `401`;
- пользователь перечитывается из БД **с фильтром `deleted_at IS NULL`**, поэтому изменение прав, роли и увольнение сотрудника вступают в силу при следующем обновлении;
- приостановленный или просроченный арендатор — `403 TENANT_INACTIVE`.

Отзыв семьи токенов **до 2026-08-24 не работал**: `UPDATE ... revoked_at` выполнялся внутри транзакции, из которой затем бросалось исключение, и `ROLLBACK` его отменял. Утечка токена приводила лишь к тексту ошибки, а все остальные сессии пользователя продолжали действовать — то есть ветка, написанная ради обнаружения кражи, не давала никакого эффекта. См. `M0.12.15`.

**Ошибки:** `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 TENANT_INACTIVE`.

## 11. Проверка токена на защищённых маршрутах

Хук `authenticate` (`onRequest`), зарегистрированный в каждой защищённой группе:

1. Пропускает публичные пути: `/auth/otp/send`, `/auth/otp/verify`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/register`, `/auth/slug-available`, `/auth/code/request`, `/auth/code/status`, `/auth/login/verify`, `/auth/telegram/webhook`, `/auth/max/webhook`, `/auth/forgot-password`, `/auth/reset-password`, `/health`.
2. Требует заголовок `Authorization: Bearer …`, иначе `401` («Missing bearer token»).
3. Проверяет подпись и срок; при ошибке — `401` («Invalid or expired token»).
4. Требует строковые `sub` и `tenant_id` в полезной нагрузке, иначе `401` («Invalid token payload»).
5. Отклоняет токены с `typ`, отличным от `access` — `401` («Invalid token type»).
6. Загружает пользователя запросом `WHERE id = $1 AND tenant_id = $2`; если строки нет — `401` («User not found»).
7. Заполняет `request.authUser`, `request.tenant_id`, `request.permissions`, `request.installed_modules`.

Сбои БД сознательно не перехватываются как `401` — они дадут `500`, чтобы недоступность базы не выглядела как проблема с токеном.

> Плагин обёрнут в `fastify-plugin`. Это существенно: без обёртки `addHook` привязывается к собственному контексту инкапсуляции плагина, и хук не выполняется ни для одного маршрута — именно этот дефект приводил к тому, что все защищённые префиксы отвечали `401 "Authentication required"` из `authorize.ts`. Скоуп при этом сохраняется: хук поднимается только до контекста группы, которая его зарегистрировала, и не затрагивает публичные `/auth/*` и `/health`.

## 15. Хранение и очистка строк аутентификации

Пять источников строк, ни один из которых прежде не очищался (`M0.8.12`): `otp_codes`, `auth_sessions`, `password_reset_tokens`, `refresh_tokens` и токены приглашений в `users`. Объём растёт линейно от трафика — строка на каждую попытку входа и на каждое обновление токена, — потому что код, сессия и ссылка только помечаются `consumed_at`, а refresh-токен `revoked_at`.

`services/auth-maintenance.service.ts` выполняет очистку раз в сутки в процессе API. BullMQ не используется: Redis в развёрнутом стеке отсутствует, и очередь пришлось бы вводить вместе с новым сервисом ради одной периодической задачи. Работа идемпотентна, поэтому повторный или пропущенный прогон безвреден, а при нескольких репликах лишний прогон удалит уже удалённое.

| Таблица | Срок после истечения | Почему не сразу |
|---|---|---|
| `otp_codes` | 1 день | удалив просроченный код немедленно, сервер отвечал бы «Неверный код» вместо «Срок действия истёк» — это разные указания пользователю |
| `auth_sessions` | 1 день | то же |
| `password_reset_tokens` | 7 дней | `requested_ip` — единственный след того, кто запрашивал восстановление; нужен при разборе жалоб на чужие письма |
| `refresh_tokens` | 30 дней | отозванный токен нужен для обнаружения утечки: ранняя очистка превратила бы кражу в обычный `401` без отзыва остальных сессий |
| `users.invite_token_hash` | 7 дней | снимается **только токен**; строка сотрудника остаётся |

Строка приглашённого сотрудника не удаляется автоматически: она занимает место в тарифе и видна администратору со статусом «Приглашён». Молчаливое исчезновение сотрудника из списка через неделю вместе с уменьшением счёта — решение уровня администратора, а не задачи обслуживания.

`refresh_tokens.replaced_by` ссылается на ту же таблицу без `ON DELETE`, поэтому прямое удаление родителя отклонялось бы с `23503`. Ссылки на удаляемые строки сначала обнуляются, затем выполняется `DELETE` — обе операции в одной транзакции, поэтому вся просроченная цепочка ротации исчезает за один прогон. `ON DELETE CASCADE` здесь неверен: он снёс бы вместе со старым звеном все более новые, включая действующую сессию. Обнуление безопасно — `replaced_by` служит только для разбора инцидентов и в логике входа не участвует.

Оба бот-токена и SMTP необязательны намеренно: недоступность одного канала не должна останавливать API, поэтому она проявляется как `503` этого канала, а не как отказ запуска. Но канал либо выключен целиком, либо настроен безопасно — токен без секрета webhook запуск останавливает.

Пустая строка приравнивается к «не задано» (`optionalNonEmpty` в `config/env.ts`). Это требование docker-compose: форма `${VAR:-}` подставляет в контейнер именно `""`, а не отсутствие переменной, поэтому обычный `.optional()` проверял бы `""` против формата и превращал необязательную переменную в отказ запуска. Прежний инлайновый фолбэк `"change-me-in-production"` для `JWT_SECRET` удалён — production не может подняться с публично известным секретом. Полный список переменных — `backend/.env.example`.
