## 1. Слаги каналов

| Слаг | Название | Иконка | Маршрут интерфейса |
|---|---|---|---|
| `telegram` | Telegram | `Send` | `/integrations/telegram` |
| `whatsapp` | WhatsApp | `MessageCircle` | `/integrations/whatsapp` |
| `max` | MAX | `Hash` | `/integrations/max` |
| `avito` | Avito | `Store` | `/integrations/avito` |
| `instagram` | Instagram | `Instagram` | `/integrations/instagram` |

Слаги **без префикса** `integration_`: именно эти значения лежат в
`marketplace_modules`, в `installed_modules` у существующих арендаторов и в
`entity_id` журнала `tenant_audit_log`, по которому определяется, начислялся ли
пробный период. Категория `integration` в каталоге уже отделяет каналы от прочих
модулей, поэтому префикс в слаге не добавил бы информации, а переименование
потребовало бы миграции данных в трёх таблицах.

Единый источник — `MODULE_SLUGS` и `CHANNEL_SLUGS` в `backend/src/types/index.ts`.
До их появления список модулей существовал в `ModuleSlug` и в
`marketplace.types.ts` независимо, и каналы попали только в один из них:
маркетплейс их продавал, а `requireModule` о них не знал.

---

## 2. Права и гейты

Все маршруты требуют:

1. аутентификации (`authenticatePlugin`);
2. права `tenant:admin` (`requirePermission`);
3. установленного модуля канала (`requireModuleFromParam("channel")`).

Порядок значим: право проверяется **до** установки модуля, иначе рядовой
сотрудник по URL отключённого канала узнавал бы состав модулей арендатора.

Отдельные права `channels:read` / `channels:write` не вводились: подключение
аккаунта — тарифное и техническое действие (токены ботов, авторизация), а не
рядовая работа с клиентами, поэтому они дублировали бы `tenant:admin` без
разницы в поведении.

`requireModuleFromParam` — новый декоратор: пять каналов обслуживаются одной
группой роутов, поэтому слаг известен только в момент запроса. Значение сверяется
с закрытым списком `MODULE_SLUGS` до обращения к установленным модулям —
произвольная строка в URL даёт `404`, а не `403 MODULE_NOT_INSTALLED`, иначе
опечатка в пути выглядела бы как отключённый модуль.

## 3. `GET /api/v1/channels/:channel/accounts`

Подключения канала и сводка по тарифу одним ответом.

```json
{
  "data": [
    {
      "id": "8f1e...",
      "channel": "telegram",
      "label": "Основной бот",
      "externalId": "@my_company_bot",
      "status": "pending",
      "statusMessage": "",
      "hasCredentials": false,
      "lastSyncAt": null,
      "connectedAt": null,
      "createdAt": "2026-08-23T18:20:00.000Z"
    }
  ],
  "meta": {
    "total": 1,
    "summary": {
      "channel": "telegram",
      "quantity": 3,
      "connectedCount": 0,
      "total": 1,
      "trialEndsAt": "2026-09-06T12:00:00.000Z",
      "trialActive": true
    }
  }
}
```

Сводка приходит в `meta`, а не отдельным эндпоинтом: шапка страницы и таблица
рендерятся вместе, и два запроса дали бы им разные моменты времени — счётчик
«1 из 3» расходился бы с числом строк.

`quantity` берётся из `installed_modules`, а не считается по факту: это
**оплаченное** число аккаунтов, и расхождение с фактическим — то, что страница
обязана показать.

`trialActive` считается на сервере: часы браузера можно перевести, и клиент
показал бы действующий пробный период после его окончания.

### Состояния подключения

| Статус | Подпись в UI | Значение |
|---|---|---|
| `pending` | Требуется авторизация | запись создана, авторизация не завершена |
| `connected` | В сети | канал обменивается сообщениями |
| `error` | Ошибка соединения | причина в `statusMessage` |
| `disabled` | Отключён | выключен пользователем |

`pending` отделён от `error` намеренно: аккаунт создан, но не авторизован — это
исходное состояние, а не сбой, и в интерфейсе они выглядят по-разному.

## 3a. Telegram: подключение пользовательских аккаунтов (MTProto)

> Источник: `backend/src/modules/channels/telegram-mtproto.service.ts`,
> `telegram-auth.service.ts`, `telegram-integration.routes.ts`,
> `backend/src/db/migrations/0013_telegram_mtproto.sql`.
> Добавлено 2026-08-23.

Смонтировано под `/api/v1/integrations/telegram`. Гейты те же: `tenant:admin`
плюс установленный модуль `telegram`.

Telegram **не подключается** через `POST /channels/telegram/accounts` — этот
маршрут отвечает `400 CHANNEL_REQUIRES_AUTH_FLOW`. Ручная запись оставила бы в
списке аккаунт без сессии: он выглядел бы подключённым, не работал и занимал
место по тарифу.

### Это не бот

`TELEGRAM_AUTH_BOT_TOKEN` (Bot API) доставляет коды входа в саму CRM.
`TELEGRAM_API_ID` / `TELEGRAM_API_HASH` (MTProto, my.telegram.org) подключают
аккаунт пользователя, чтобы CRM видела его личную переписку с клиентами. Разные
подсистемы, разные переменные.

Без ключей MTProto маршруты отвечают `503 TELEGRAM_MTPROTO_UNAVAILABLE`;
остальной API работает. Заданный только один ключ из пары останавливает запуск —
проверка в `config/env.ts`.

### Почему два запроса и зачем состояние в БД

MTProto привязывает `phone_code_hash` к auth_key **конкретного соединения**.
Новый клиент с пустой сессией получил бы `PHONE_CODE_INVALID` на верный код,
поэтому между шагами сохраняется сериализованное состояние клиента
(`telegram_auth_sessions.session_state`, TTL 10 минут). Хранится в БД, а не в
памяти процесса: контейнер перезапускается, и незавершённая авторизация не должна
ломаться. Redis в проекте пока нет.

Состояние **зашифровано**: даже незавершённая сессия содержит auth_key соединения
с Telegram.

### `POST /auth/send-code`

```json
{ "name": "Рабочий номер", "phone": "+7 985 501-40-40" }
```

Телефон нормализуется до `+` и цифр на сервере. Ответ:

```json
{
  "data": {
    "tempSessionId": "b1d4ee0a-…",
    "phoneCodeHash": "d3b948dbc41df0d884",
    "isCodeViaApp": true,
    "expiresAt": "2026-08-23T19:23:15.555Z"
  }
}
```

Лимит тарифа и повторная привязка того же номера проверяются **до** отправки
кода: иначе пользователь получил бы SMS, ввёл код и только тогда узнал, что
аккаунт подключить нельзя.

### `POST /auth/sign-in`

```json
{ "tempSessionId": "b1d4ee0a-…", "code": "53193" }
```

`phone`, `phoneCodeHash` и `name` в теле **не принимаются**, хотя задание их
перечисляет: они уже сохранены на первом шаге. Иначе подменой этих полей можно
было бы завершить подключение под чужим номером, а `phoneCodeHash` от другой
сессии сломал бы вход.

Два возможных ответа, оба `200`:

```json
{ "data": { "status": "password_required", "requires2FA": true,
            "passwordHint": "gen26", "message": "Требуется облачный пароль (2FA)" } }
```

```json
{ "data": { "status": "connected", "requires2FA": false, "accountId": "838b3473-…" } }
```

`200`, а не `400`, при запросе пароля: код уже принят, авторизация продолжается —
это следующий шаг мастера, а не ошибка ввода. Задание допускает оба варианта.

Для второго шага пароль передаётся тем же маршрутом **без кода**: код
одноразовый, и повторный `auth.SignIn` Telegram отклоняет. Признак `requires_2fa`
хранится в сессии, поэтому ветвление идёт по нему, а не по наличию кода в запросе.

```json
{ "tempSessionId": "b1d4ee0a-…", "password": "…" }
```

2FA считается по SRP (`computeCheck` из GramJS): пароль не уходит в Telegram ни
открытым текстом, ни хешем.

### Ошибки

| Код | HTTP | Причина |
|---|---|---|
| `TELEGRAM_2FA_REQUIRED` | 409 | пароль нужен, но не передан (при прямом вызове API) |
| `TELEGRAM_CODE_INVALID` | 400 | неверный код |
| `TELEGRAM_CODE_EXPIRED` | 410 | код истёк |
| `TELEGRAM_PASSWORD_INVALID` | 400 | неверный облачный пароль |
| `TELEGRAM_SESSION_EXPIRED` | 410 | 10 минут на подключение истекли |
| `TELEGRAM_TOO_MANY_ATTEMPTS` | 429 | 5 неверных попыток — сессия закрыта |
| `TELEGRAM_FLOOD_WAIT` | 429 | ограничение Telegram, в тексте указано время |
| `TELEGRAM_PHONE_BANNED` | 403 | номер заблокирован в Telegram |
| `TELEGRAM_SIGNUP_REQUIRED` | 400 | за номером нет аккаунта Telegram |
| `TELEGRAM_AUTH_RESTART` | 409 | Telegram прервал авторизацию, начать заново |

Строки протокола (`PHONE_CODE_INVALID`) наружу не отдаются — они ничего не
говорят человеку, вводящему код. Попытку расходуют только ошибки ввода: сбои сети
и конфигурации не приближают к блокировке.

### `POST /accounts/:id/check`

Проверяет, жива ли сохранённая сессия (`{"alive": true}`), и обновляет статус
подключения. Нужен потому, что пользователь может отозвать сеанс в приложении
Telegram, и подключение продолжало бы отображаться активным.

### Что сохраняется в `channel_accounts`

| Поле | Значение |
|---|---|
| `channel` | `telegram` |
| `label` | название из мастера, иначе имя из профиля Telegram |
| `external_id` | `@username`, иначе номер, иначе id |
| `remote_user_id` | числовой id пользователя Telegram |
| `status` | `connected` |
| `credentials` | `{ session: "v1:…", tgUserId, username }` — сессия зашифрована |
| `credentials_encrypted` | `true` |

`ON CONFLICT` обновляет существующую строку: переподключение того же аккаунта
после отзыва сессии — обычный сценарий и не должно упираться в уникальный индекс.

## 4. `POST /api/v1/channels/:channel/accounts`

```json
{ "label": "Основной бот", "external_id": "@my_company_bot" }
```

`201` с объектом подключения. Ошибки:

| Код | HTTP | Причина |
|---|---|---|
| `CHANNEL_LIMIT_REACHED` | 409 | подключений уже столько, сколько оплачено |
| `CHANNEL_ACCOUNT_EXISTS` | 409 | этот `external_id` уже привязан к каналу |
| `MODULE_NOT_INSTALLED` | 403 | канал отключён в маркетплейсе |
| `VALIDATION_ERROR` | 400 | пустое название или идентификатор |

Лимит проверяется на сервере, а не только в интерфейсе: число аккаунтов —
тарифная величина, и запрос можно отправить минуя UI, получив канал с пятью
подключениями по цене одного. Кнопка в интерфейсе при исчерпанном лимите
**скрывается**, а не блокируется, и вместо неё показывается ссылка в маркетплейс.

Повтор `external_id` отклоняется частичным уникальным индексом
`idx_channel_accounts_unique_external` (по живым строкам): иначе сообщения
приходили бы в два подключения, а тариф считал бы два аккаунта. Индекс частичный,
чтобы удалённое подключение не мешало привязать тот же аккаунт снова.

## 5. `PATCH /api/v1/channels/:channel/accounts/:id`

Принимает любое подмножество: `label`, `status`, `status_message`, `credentials`.
Пустой объект отклоняется — `VALIDATION_ERROR`.

`connected_at` выставляется вместе с первым переходом в `connected` и только при
первом: иначе повторная авторизация переписывала бы дату привязки, а она нужна в
таблице как «с какого момента канал работает».

---

## 6. `DELETE /api/v1/channels/:channel/accounts/:id`

`204`. Мягкое удаление (`deleted_at`), а не `DELETE`: на аккаунт канала со
временем будут ссылаться сообщения, и жёсткое удаление оставило бы переписку без
источника. Освобождает одно оплаченное подключение.

## 7. Хранение секретов

`credentials JSONB` содержит токены авторизации и **никогда не покидает сервер**:
в выборках вместо колонки отдаётся признак `(credentials <> '{}') AS
has_credentials`. Клиенту нужен только факт заполненности, а попадание токенов в
ответ API означало бы утечку при первом же логировании запроса на клиенте.

**Шифрование at rest реализовано** (`services/credentials-cipher.ts`,
AES-256-GCM, конверт `v1:<iv>:<tag>:<ciphertext>`). Ключ —
`CREDENTIALS_ENCRYPTION_KEY`, обязателен когда включён MTProto.

Причина не формальная: сохранённая MTProto-сессия даёт **полный доступ к аккаунту
Telegram** — чтение всех личных чатов и отправку от имени владельца. Дампа БД или
резервной копии достаточно, чтобы получить чужие переписки, а RLS от этого не
защищает: она ограничивает запросы приложения, а не доступ к файлам базы.

GCM, а не CBC: аутентификация шифротекста означает, что подмена значения в БД
обнаруживается при расшифровке, а не приводит к попытке подключиться подставленной
сессией. Версия в префиксе позволяет сменить ключ или алгоритм без миграции
данных.

Ротация ключа пока не автоматизирована (`M7.5.12`): смена
`CREDENTIALS_ENCRYPTION_KEY` сделает существующие сессии нечитаемыми, и аккаунты
придётся подключить заново.

## 8. Отключение канала в маркетплейсе

Каналы делят одну таблицу `channel_accounts`, поэтому очистка данных при
отключении фильтрует по `channel` (`ModuleDataService.channelFilter`). Без
фильтра отключение Telegram скрыло бы и аккаунты WhatsApp — у пяти модулей общая
таблица, и условие только по `tenant_id` их не различает.

Правила те же, что у остальных модулей: мягкое удаление, окно восстановления
30 дней, повторное подключение возвращает ровно те строки, которые скрыло
отключение. Диалог подтверждения называет число затронутых подключений через
`GET /marketplace/modules/:slug/impact`.
